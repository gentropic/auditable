Getting started

1What micro is

micro is a single self-contained HTML file — a viewer that grew into a workbench. It streams massive spatial-element files (never holding them fully in memory), so the first look is near-instant at any size and the picture densifies while you orbit.

It reads:

  • Point clouds — LAS, PLY, XYZ / PTS / DAT dumps
  • Block models — CSV / TXT, Datamine .dm, and Parquet, sub-blocked included
  • Grids — GeoTIFF, Surfer .grd, ESRI ASCII .asc
  • Meshes & CAD — .msh (Leapfrog), OBJ, PLY-with-faces, LFM, Datamine wireframe pairs, DXF, .wfr — see Meshes
  • Strings & polygons — pit limits, leases, blast outlines as features with their attributes: CSV string files, WKT, shapefiles, GeoJSON, KML / KMZ, DXF, and the QGIS clipboard — see Strings & polygons
  • Projects from other software — OMF (.omf) block models, points, and surfaces, a layer each
  • Tables — CSVs without coordinates and Excel workbooks, a sheet each — see Tables
  • Drillholes — collar + survey + interval tables (desurveyed on load); a set can carry several interval tables (assays, lithology, geotech) sharing one geometry — see Drillholes

Beyond viewing, it does the everyday resource-geology work: filter and section; derive columns by expression, lookup, broadcast, or resampling; domain by a solid; join and reconcile model versions; grade–tonnage, swath, and validation analysis; figure export. All of it runs against the source file, offline, with the provenance kept.

What micro is for — micro shows your data and checks it: view, query, section, pick, measure, join, reconcile, validate, convert. It is not an estimation or modelling suite — it doesn't interpolate grades, build geological models, classify resources, or write reports, and that boundary is deliberate. micro is the honest lens, not the resource factory.

How micro thinks

Four ideas explain almost everything else in this manual:

  • A dataset is an element. A block model, a drillhole set, a grid — each is a table (or several, for drillholes) plus an interpretation of its geometry. The records are positional: row 173 of the file is block 173 everywhere, forever.
  • Columns are the atoms. Source columns come from the file; derived columns — calculated, materialized, painted, joined, broadcast — behave identically once they exist. Everything downstream (filter, color, analysis, export) consumes columns and doesn't care where they came from.
  • Operations are recorded, not just run. Every derivation is written down as data — the expression, the method and parameters, the inputs — in the project's element manifests (§39). What was done is always readable, and re-runnable.
  • Nothing is imported. micro reads your files where they are, streams them, and keeps its own additions beside them — sidecar columns, manifests, caches. Delete micro's files and your data is exactly as it was.

Tools → Settings… holds the machine preferences — the theme (dark basalt, light equipment gray, or follow the system; also View → Theme and ⌘K “theme”), background (by default it matches the theme), render budget, selection-tool stickiness, GPU/CPU compute, auto-optimize-on-save, ambient occlusion, software rendering, the natural-language command bar — stored in this browser only. View state (camera, sections, pinned windows) travels with the project; data decisions live in its manifests.

Language. Settings → display → language (or ⌘K “language” / “idioma”) switches the interface between English and Português (Brasil), live. It covers the menus and every right-click menu, the window titles, the command palette — which searches in both languages whichever is showing, so “envoltória” and “grade shell” find the same command — the toolbar and these settings. Status messages, the in-app Help and this manual are in English for now. micro starts in English and never switches by itself: in a browser set to Portuguese, the start screen offers “Interface em português” once. The choice is remembered on this machine.

Custom themes. Theme → custom… (or Settings → display → custom theme → edit…) opens the theme editor: a swatch for every colour the panels use — surfaces, text, accents — over the dark or light register you start from, applied as you pick. A contrast line reads every ink people actually read against the surface it sits on and flags any pair below 4.5:1. start from… offers dark, light and a shipped high contrast theme. A theme can carry its own 3D background, used while Settings → background is “match the theme”. export .json saves it as a small file (only the colours that differ from its base) and import… loads one, so a team can share a look. Like every preference, the theme stays on this machine; it never travels inside a project.

Tip — The fastest way to reach anything is the command palette: Ctrl/⌘K (or the ⌘K button). It searches every action and shows only what applies to the layer you have selected.

2Getting started

Opening data

Drag a file (or several) anywhere onto the window, or use File → Open…. Several files at once become separate layers. The open dialog shows each file's detected role — an Open as ▾ on every row lets you override it (a block model as points, a PLY mesh as points, a delimited file as collar / survey / intervals), and drillhole trios assemble themselves from those roles. What micro detected — the column mapping, the grid, the decimal mark, anything it couldn't read — is in file info (i), and correctable there.

No data handy? The empty state offers ▸ open the demo project — one click generates a full scene locally: a 1.8M-block iron model with realistic bimodal grades, a drillhole set threading the ore, pre-mining topography, three pit-phase shells, and the ore-shell mesh the holes chase — sectioned open on the lens, with a grade–tonnage curve already computed. Every workflow in this manual can be tried on it, and File → Save project as… writes it to a real folder you can inspect: plain CSVs, JSON manifests, no black box.

The layers panel

p toggles the layers panel. Each opened dataset is a layer with its own color, filter, and visibility. Layers can be grouped and reordered by dragging; [ ] step the active layer, h hides/shows it, ⇧H solos it (press again to restore what was visible). Drillhole sets appear as their own group with collar and survey rows — see Drillholes.

Right-click a layer for its menu. It lists only what applies to that layer, always in the same order: the things you reach for most at the top — Zoom to layer, Rename layer…, Hide layer, Properties…, Attribute table…, Filter… — and everything else in submenus named like the menu bar's: Analyse (stats, grade–tonnage, swath, QA, factors…), Select, Views, Display (opacity, edges, sections, style), Data & file (reinterpret, reload, change file, Store as Parquet, export, file info, lineage), Move, and Remove layer last. A mesh and a grid add a Geometry submenu, for what a surface or a solid does to other layers. A submenu with nothing in it for that layer is left out.

Mutually exclusive groups. Right-click a group → Mutually exclusive and it shows one child at a time, like a radio group in QGIS: the children get round eyes, and turning one on turns the others off. That holds however you turn it on (the eye, h, the palette, the context menu). Showing none is fine. A subgroup counts as one child. { } step through the group around the active layer, and the active layer follows, so you can flip through pit phases without the mouse. Flagging a group keeps its topmost shown child. Scenes and bookmarks restore exactly what they saved.

F2 renames the active layer. Rename layers… (on a group, a multi-selection, or the palette) batch-renames: one-click strip the common prefix/suffix, or find→replace with optional regex, with a live before→after table.

Getting around

Drag to orbit, right-drag (or shift-drag) to pan, wheel to zoom. f fits the data. n s e w look level that way, d is plan, o toggles orthographic (needed for a true scale bar). Click a block or point to pick it — the record panel shows its full source row, calculated and derived columns included, with a fields picker to trim it to the columns you care about.

Vertical exaggeration — the Z× box on the instrument rail (or View → Vertical exaggeration) stretches the whole scene vertically so subtle relief or a flat-lying ore lens reads. It's a property of the view, not one layer: every layer stretches together and stays registered, and it's display-only — picking, measuring, and section cutting all stay in true coordinates. It travels with bookmarks and scenes.

Asking in plain words

Alt+K opens the plain-language bar: type what you want the way you would say it — blocks above 55 Fe in hematite, select inside the ore shell, swath of FE along x — in English or Portuguese (seção na cota 600, esconde a topografia). The ⌘K palette falls back to it when nothing you typed matches a command name.

The bar proposes; it never acts. It answers with one row that spells out the command it understood — a filter shows the very expression it will put in the box, FE > 55 and LITO == "HEMATITE", and the layer it will act on — and nothing happens until you read it and press Enter. It understands filters (and clearing them), selecting by conditions or inside a solid, colour by a column, a section at a position and its thickness, vertical exaggeration, the background, the analysis windows (each opens set up from the phrase; Run stays yours), projections, export rows, and showing or hiding a layer or group. Anything else gets not understood — nothing proposed, on purpose: a wrong guess costs more than a refusal, and words that destroy (delete, exclui) never produce a proposal at all.

The bar learns this project: on first use it builds its vocabulary from your columns, category values and layer names and trains on them in the browser, in under a second. No model is downloaded and nothing leaves the machine. Settings → interaction → natural-language command bar turns it off.

Without a graphics card

On a machine with no usable graphics card — a virtual machine, a remote desktop, a locked-down laptop — the browser draws on the processor instead, many times slower. micro notices at start (software rendering detected — reduced detail) and adapts: a render budget of 0.1M elements a frame instead of 1M (unless you set your own), the view drawn when something changes rather than continuously, eye-dome lighting off, ambient occlusion off, and picks rendered on click. The picture is less dense and takes longer to settle; nothing else changes. Settings → display → software rendering overrides the detection (automatic · on · off), and Help → About micro says what draws the view.

3A guided tour

Twenty minutes, no data needed, every major idea once. Open micro and click ▸ open the demo project on the empty state — it generates a small mining scene locally: a 1.8M-block iron deposit (cut open on an E–W section), a twelve-hole drilling program threading it, pre-mining topography, three pit-phase shells, and the orange ore-shell mesh. A grade–tonnage window is already computed on the right.

1 · Look around

Drag to orbit, wheel to zoom, f to fit. The deposit is colored by iron grade — the yellow core is the lens. Hold Ctrl and roll the wheel: the section scrubs through the deposit, and watch the orange ring on the cut face — that is the ore shell's trace, the mesh drawn where the plane cuts it, with the topography a thin line above. Press l to face the section square-on. In the layers panel (p), open mining phases and toggle the phase shells; every layer has its own eye.

2 · Ask a question — the filter

Press / and type FE > 55, then Enter. The deposit reduces to its high-grade core, live, and the status bar counts the matching blocks. Now click the ▾ beside the filter box: the drawer opens with your expression as a slider. Drag it — the threshold, the expression text, and the model all move together. Use add condition… to bring LITO in, click a chip to switch lithology, then remove the row with its ×. Nothing you do in the drawer is different from typing — it is typing, done for you.

3 · Meet the drillholes

In the layers panel, the demo group is the drillhole set: a ◈ collars row, a ↧ survey row, and the assay intervals. Click ◈ collars → Attribute table… — twelve holes, and notice EOH and COMPANY: PIONEER's early scout holes stopped at 150 m, MERIDIAN drilled to the floor. Now ◈ collars → Filter holes… and type COMPANY = "MERIDIAN" — the scout holes vanish from every interval table at once, because the filter lives on the collars and flows down the hole relation. Clear it (empty expression), then try Broadcast column to intervals → EOH: every interval now carries its hole's depth as a real column — color by it, filter EOH > 200, export it.

4 · Derive something — the ƒ workbench

Select the deposit layer, then Tools → Calculated columns…. Name a column CLASS and type:

if(FE > 58, 2, if(FE > 45, 1, 0))   # 2 = high grade, 1 = mid, 0 = waste

Below the editor the ladder appears as a case table — each condition a row of widgets, each value a slider. Save it, then pick ƒ CLASS in the color dropdown: the deposit repaints as three grade classes. Go back to the window and drag the 58 slider — the model re-classes as you drag. That loop — define, color, tune — works for any expression over any columns, including the ones you just broadcast.

5 · The curve — grade–tonnage

In the grade–tonnage window, set density expr to SG (the model carries specific gravity), cutoffs to 40, and Run. Real tonnes, forty cutoffs, both curves. Hover the plot to read values; ⧉ table puts cutoff · tonnes · grade on the clipboard for a spreadsheet. Try scope: filt with your FE > 55 filter still on — the curve recomputes for the filtered core only.

6 · Make the figure

View → Decorations & figure…: turn on the scale bar, north arrow, and legend, give it a title, set the background to white, and Export figure. The PNG on your disk is exactly what you saw — report-ready.

7 · Keep it

File → Save project as… (Chromium) writes everything to a folder. Open that folder outside micro: models/ and drillholes/ hold plain CSVs, project.json the view state — and beside the deposit, deposit.csv.element.json. Open it in a text editor: your CLASS expression is recorded there as an operation, inputs and all. That file is the audit trail — everything you derived, readable without micro. Reopen the project any time; it comes back exactly as you left it, windows included.

Where next — deeper on each idea: the filter · the ƒ workbench · drillholes · join & reconcile · the project store. Your own data works the same way — drag it in.

4Viewing & sections

Color

The color dropdown drives the active layer: by elevation, a numeric channel (a grade), a category (a rock type), rules, a painted column (✎), a materialized column, or a calculated column (ƒ — see the ƒ workbench). Properties → style holds the rest, as a mode (continuous · categorized · rule-based · solid) and a column; calculated and materialized columns are columns there like any other. The min/max boxes clip the scale so outliers stop eating the ramp — the clip belongs to the column, so FE's 40–65 doesn't flatten SG when you switch, and comes back when FE does. A clipped end says so in the legend (≤ 40, ≥ 65).

Grade classes. Pick a ramp (viridis · spectral · magma · turbo · greys · rdbu), type breaks — 20, 40, 55, 60, 65 — and tick classed: six classes, < 20, 20 – 40 … ≥ 65, each a solid colour you set on its chip. A class is its interval: the colour stays with it whatever the data range, the clip or the layer, so the drillholes coloured by the same classes read like the model. On a scanned column the histogram is the editor — drag a break, double-click to add one (both halves keep the colour), right-click to remove one (the lower class's colour stays) — and every row shows its count and share; quantiles and equal make breaks for you. Each class has an eye: a hidden class isn't drawn, can't be picked, and leaves the legend. Every edit is one undo step.

No data. A blank value draws in its own colour (grey by default) — never as the lowest grade. The no data row sets the colour or hides blanks, and shows how many there are once the column is scanned; the legend lists it. A value that means blank, such as a -99 sentinel, is a number until you say otherwise: right-click the column → Detection limits & blanks → Values that mean blank… (CSV and drillhole tables; Datamine and Parquet keep their own nulls).

Rules. Rule-based mode colours by ordered expressions in the filter language — FE >= 55 and LITO = "HEMATITE" — first match wins, with everything else last; each rule has a colour, an eye and a live count.

Reusing a style. Right-click a layer → Style → Copy style, then Paste style on another layer — the drillholes, next month's model, a layer in another project (the copy also goes to the system clipboard). Everything is matched by column name: the classes land on FE wherever FE sits in the other file, a category legend on a same-named category column; the status line says what applied and what had no match. Save style… writes it as a .microstyle.json file and Load style… applies one. Change file… keeps a layer's look by column name the same way.

The legend draws what the model draws — classes as swatches in their colours, a continuous ramp as its bar, categories by their labels (hidden ones left out), rules by their names — under the column's name; two legends on one column say whose they are.

Point clouds colour by elevation, intensity, classification or RGB, and by any other column their points carry. For a LAS file that is the whole point record — return number, number of returns, scan angle, user data, point source id, GPS time, red/green/blue, NIR — plus the extra bytes the file declares (named per-point attributes such as reflectance or deviation, with their scale and no-data value). For a PLY it is every vertex property. The column is read once onto the GPU, so switching back is instant, and a no-data value stays out of the colour range. The filter box takes the same columns — return_number = 1 and reflectance > 20 keeps first returns above 20 — reading only the columns the expression names, and a no-data value is blank there too, never zero. Clicking a point shows its whole record, and Attribute table… lists the points. A cloud is also a table to the analysis windows: Stats… and Scatter / Q-Q… take its columns, a cloud can be the samples of Block vs sample, and it can be a series beside a model in a swath. Grade–tonnage, the cross-tab and swath of the cloud itself stay block-model tools — they need block volumes. Point size in a cloud's right-click menu makes it draw bigger or smaller than the global point size (×1 to ×8), and it is saved with the project.

Sections

A section is a live cut, and on block models it is a true cut: each block is clipped analytically against the slab faces, so the cut paints a continuous wall — with the block's color — instead of a ragged centroid cull, and the wall itself is pickable.

A layer's own slab. Right-click a layer → Cut by sections ▸ follow, with its own slab… and give it a ± width in metres: it's cut around the same plane, moving with the section, but with its own thickness. The section bar's slab still applies to every other layer. A thin slab of the model with a thick slab of holes or a surface around it is the usual use. The menu says Cut by sections (± 50 m) while it's set, and it's saved with the project and in scenes.

Meshes and surfaces draw their trace on the wall. A sectioned mesh doesn't hide the cut face: it renders as its intersection trace — a closed ore shell becomes an outline ring around the grade zone it encloses, a topo surface a thin line across the top — flattened onto the section face like a drafted section plot. The trace width follows the section-width control. A layer that should stay whole (topo for context, the drillholes threading a cut model) sets right-click → Cut by sections → don't cut.

Pick a preset (plan · N–S · E–W), press k and drag a line (⇧ snaps 15°, ⇧⌥ 5°), or type a plane's dip-direction + dip. x toggles it, l faces it, ⇧L faces its back. , . step one slab at a time, and Ctrl+wheel scrubs the position continuously; Alt+wheel thickens or thins the slab. Follow makes the camera ride along as you scrub; 2D locks the view flat onto the section — drags pan instead of orbit — for section-by-section interpretation. Per layer, Cut by sections picks how the section treats it: follow (the slab), keep front only / keep behind only (a half-space split at the plane), or don't cut.

Picking & the record panel

Click any block, point, or interval to pick it: the record panel (right) shows the full source row — every column, including calculated, estimated, painted, and broadcast ones, each labeled by kind. The fields picker (search + all/none) trims the panel to the columns you care about, per layer, and the choice persists with the project. Picking works on section walls too — the block behind the cut face answers. In the attribute table the link runs both ways: click a row to pick it in the scene, pick in the scene to highlight the row.

Measure

m arms the tape: click two records and read 3D distance · plan distance · Δz in the status bar — bench heights, hole spacing, the plan width of a zone. The measurement anchors to picked records (not screen pixels), so it is exact in world coordinates and unaffected by vertical exaggeration. Press m again or Esc to put the tape away.

Block edges

⇧B (or View → block edges) outlines every block — the classic wireframe-over-solid look for checking sub-blocking or lattice alignment. Each layer can override the global toggle from its context menu (always / never / follow).

Ambient occlusion. Eye-dome lighting darkens where the depth jumps — a silhouette, a pit rim — but not where two surfaces meet at an angle. Settings → display → ambient occlusion (soft · medium · strong) adds that shade along every inner corner: the foot of a pit wall, the step between benches. It is mostly for figures, which render with it; it is off by default, off under a projection and off in software rendering.

Projections — the highest grade through the model

A model drawn normally shows its surface. View → Projection (or ⌘K “projection”) answers a different question: for every pixel micro takes every block the line of sight passes through and keeps one value, coloured through the layer's own ramp. Max is where the best rock is, anywhere along the ray — a high-grade lens shows through a low-grade cap; Min is the waste behind good blocks; Mean the average along the ray. It applies to block models and clouds coloured by a numeric column, and respects the section slab (a one-bench plan slab is the best grade on that bench — step it with , .), the filter, the clip and hidden classes; blanks never count. A click picks the block that is the pixel's value. While the picture fills in, the status line reads MIP (partial …); wait for MIP (exact) before reading a value off it (an exported figure is always exact).

Projection to grid… (same menu) asks the same question of every record and writes the answer as a grid layer you can contour, drape or export: per plan node, the max, min or thickness-weighted mean along the column, or — above a cutoff — the ore thickness, the accumulation (grade × thickness), tonnes or metal. A block counts by the length of the vertical line inside it, so sub-blocks and rotated models count true. The filter applies, and an inside row limits it to polygons; the routine tool is projectgrid.

Views — one model, shown again

To see one block model two ways at once — copper on one side, gold on the other, or two filters over regions that don't overlap — you don't load it twice. Right-click the layer → New view of this layer (or New view beside it). A view is a second layer that draws the same data: the file is read once and the GPU holds the model once. It works on block models, drillhole interval layers and point clouds.

The view sits indented under its model with a ⧉ mark, named after what it shows (bacaba.csv · CU). What is its own: colour by, ramp, min/max, category column and legend, hidden classes, filter, opacity, block edges, visibility, and where it is drawn. What it shares with its model: the file, every column (stored, ƒ, painted), the selection, and the provenance. A column you paint through a view lands on the model, and every view coloured by it shows the stroke; selecting through a view selects the model's records.

  • Its own category column. In Properties → style → categorized, a view can class by any text column (a domain, a lithology, a hole id), without changing its model. The column is read once; the classes list, hidden classes, counts and legend work as on any layer. Past 255 different values, the rest share one grey class.
  • Drawn somewhere else. Properties → style → offset moves a view by dx/dy/dz, and beside its model places it just east of the model and its other views (New view beside it does this in one step). The move is for display only: the record panel, exports and analyses read the true coordinates. Picking, measuring and lassoing work where the view is drawn, and the section cuts it there.
  • What a view's menu leaves out. Reload, reinterpret, Store as Parquet and the column operations act on the file, so they live on the model; a view's menu has View of “…” — select it to get there.
  • Removing. Removing a view asks nothing. Removing a model asks first and names its views, which go with it.

In a project a view is saved as display settings that name its model, never as a second copy of the file, and it comes back on reopen with its colour, filter, classes and offset. If the model re-reads its file (reload, re-mapping, re-desurvey), its views follow.

Exploded views

Right-click a group → Explode… pulls its layers apart so each can be seen whole: a slider sets the gap and a choice sets the direction (up, east or north). Layers stack in list order, the top of the list highest. home puts them all back. Any single layer can be moved the same way from Properties → style → offset (dx/dy/dz) — to pull one wireframe revision aside next to another, say.

It is display only. Every layer keeps its data where it is: filters, selections, grade–tonnage, swath, exports and joins read the true coordinates. A pick on a moved layer shows the true record and says “drawn displaced”; a measure is drawn where you click but reads the true positions, and says so. A figure with displaced layers carries a footnote, since the distances between them are not real. Offsets are saved with the project.

5Windows, undo & safety nets

The analysis, table, calculations, QA, and paint windows are all draggable and pinned to their layer (open several at once). View → Windows… lists every open window — click to focus, or Cascade and Close all to tidy up. The window on top carries an amber accent in its title bar; Ctrl+` cycles through the open windows.

Minimize (the – button) sends a window to a slim strip of chips above the status bar — click its chip to bring it back exactly where it was. Drag a window to the left or right screen edge to snap it to that half of the screen (a preview shows before you release). Every window kind remembers its size — and its position, when it's the only one of its kind — so your grade–tonnage window opens where you like it, every time.

Undo

Ctrl/⌘Z undoes the last step, and again the one before it: a paint stroke, a selection replaced or cleared, a filter changed from the box, a ƒ column or a styling rule removed. The status bar says what was undone, or nothing to undo. Paint strokes undo first while the brush is armed. In a text field, Ctrl/⌘Z stays that field's own text undo.

Nothing is lost without asking

  • Closing or reloading the tab with work only this session holds — an unsaved project, or a layer carrying painted or calculated columns of its own — asks first.
  • Removing a layer that carries columns of its own names them and asks; so does closing a project with unsaved changes.
  • Deleting a recipe, a bookmark, or a scene removes a file in the project, so it asks first, naming the file.
  • Long jobs stop. An export or an optimize (including the one that runs on save) shows a cancel button beside the status line while it runs. A cancelled export writes nothing; a cancelled optimize leaves the layer exactly as it was. An analysis window's Run button turns into its cancel while it scans.
Working with data

6The filter & its widgets

/ focuses the filter box. It speaks a familiar expression language over every column — source, calculated, painted, materialized, joined:

FE > 55 and LITO = "HEMATITE"
AU_OK between 0.5 and 3  or  DOMAIN in ("ORE", "HALO")
SIO2 > 10 and not (LITO = "CANGA")   # comments are fine

Matching elements isolate; everything else drops out of the render, the table, and any analysis. Enter applies, Esc clears. The box is syntax-highlighted as you type, autocomplete offers columns, functions, and category values, and unknown names get a did-you-mean. The full language — operators, functions, quoting, comments — is in the reference.

On big files the filter stays fast for three reasons: Parquet models skip whole row-groups their footers prove can't match; CSV and .dm files skip stretches via the project's band index; and after one complete scan the touched columns stay pinned in memory (see the project store). The result is that dragging a widget re-filters millions of blocks in milliseconds.

What happens to the rest — isolate, dim, ghost, outline

By default the rows a filter leaves out leave the view. View → Filter display (or ⌘K “filter display”) offers three other ways for a block model or a cloud: dim keeps the rest, darkened and opaque; ghost draws it as one flat, faint shape behind the matches — it never covers a match, so the kept blocks read whole in the shape of the model around them; outline draws only the ghost's silhouette, a thin line round the envelope of what was left out. isolate stays the fastest, since the render budget runs over the matches alone. The ghost's colour follows the background, so it reads in a figure too; the choice is saved with the layer. A drillhole filter always isolates.

The filter drawer — the expression as live controls

The ▾ button glued to the filter box opens the drawer: your current expression projected as widgets. The expression stays the single source of truth — every control rewrites its own span of the text, so the box updates as you drag and your formatting survives.

  • Numeric comparisons become sliders with a number box; between becomes a two-slider range row. The operator is a dropdown (> ≥ < ≤ = ≠ between) — switching to between converts the clause in place.
  • Category comparisons become chips — click a value to swap it, and with in (…) chips toggle membership. The op dropdown offers = ≠ in not in.
  • The AND / OR pills between rows are clickable — each one switches its own joiner in the text.
  • Brackets are real: parenthesized groups render as indented blocks with their own add condition row (inserting inside the brackets), and the top-level add offers and ( … ) to seed a new group or ( all ) or … to wrap everything so far and start an alternative branch.
  • Every row has a × to remove it — the clause and its joiner go together, removing the last condition inside brackets removes the whole group, and removing the only condition clears the filter.
  • The drawer includes a multiline editor (with # comments) for the expression itself, live-validated; reset restores the filter as it was when the drawer opened.

Add a condition from the dropdown, then reshape it entirely with the widgets — nothing is locked in at add time.

8Columns, types & the attribute table

Every dataset is a table: one record per block, point, interval, or mesh vertex, and a column per attribute. This section is about the columns themselves — how micro reads them, what it does with awkward values, and where to look at them.

The attribute table

t opens the active layer's rows as a draggable, layer-pinned window — windowed reads, so a 1.8M-row model scrolls cold. matches shows only the filtered rows, selected only the selected ones; click a row to pick it in the scene, and a pick in the scene scrolls the table to its row. Ctrl+C copies the grid selection as TSV. A drillhole set's ◈ collars and ↧ survey rows open their own tables the same way.

Column types & the scan

Properties → columns (⇧P) lists every column with its type — number or text — which decides what the filter, the colour-by, and the analyses offer. The type is sniffed from the data; if a stray unit string made a grade read as text, right-click the column → Number. scan columns streams the whole table once and fills n · mean · std · quantiles · histogram per column, calculated and derived columns included. A Parquet model shows each column's range and null count from the file's footer before any scan, and its scan runs off the page in background workers; the styling histogram scans only the column it colours by. Click a running scan to cancel it.

Detection limits

Assay tables write <0.001 for a value below the lab's detection limit, >10 above its upper limit, and codes like BDL, ND, LNR or - for no value. In a CSV block model, CSV table, or drillhole interval file, a column of numbers mixed with these reads as numeric and carries a <DL badge in Properties → columns.

micro substitutes on read: <x becomes x/2 (half the limit, the usual convention), >x becomes x, and a code is blank. Colour, filter, stats, grade–tonnage, swath, calculations, joins, and validation all see the same number; the record panel and the attribute table still show the text, and the column scan counts what was substituted (8 below detection · 2 above · 5 lab codes → blank).

Right-click the column → Below / above detection to choose <x → x/2, x, 0, or blank; >x → x or blank; and whether a negative value means below detection (some labs write -0.001 for <0.001 — off by default, because -99 usually means missing). The rule is saved with the project. A CSV export writes the values as the file had them unless you tick write <x / >x as their substitutes; a Parquet export always writes the number. Datamine .dm and Parquet columns are typed already, so this doesn't apply to them.

Decimal commas

A semicolon-separated file whose numbers are written 1,5 — the Brazilian and European convention — is detected from its data rows and read as numbers everywhere: coordinates, grades, the qualifier's <0,05, and the background scans. File info (i) says which decimal mark was found. Exports offer the decimal comma too.

Blanks

A blank is never a zero. A blank grade is unestimated: it drops out of means, curves, and the colour scale. A block with a blank coordinate isn't drawn (it would land at the origin), and isn't a record of the analyses either. In drillhole tables a blank coordinate, survey value, or interval depth is dropped and reported — see Drillholes.

9Block models — regular, sub-blocked, rotated

A block model is a table of centroids that sits on a lattice. micro finds the lattice from the coordinates themselves (a CSV or .dm needs nothing else) and draws every block as a true box, with true sections and exact picking. When the centroids don't sit on any lattice, the model opens as points — everything still works, the blocks just draw as dots.

Sub-blocked models

micro reads sub-blocked (octree) block models — where cells are refined into smaller boxes near a boundary or a high-grade zone — and renders each block at its true size, straight from the file. CSV/Parquet models with per-block dX/dY/dZ columns and Datamine .dm models with per-record XINC/YINC/ZINC are detected automatically; the model streams, picks, filters, and colours like any other. Grade–tonnage and swath weight each block by its own volume, and join and reconcile aggregate sub-blocks onto a regular grid by volume — see Join & reconcile.

Note — Any whole-number refinement works, odd ratios included, with any number of distinct shapes: each block carries its size in steps of a fine lattice (half the step every size is a whole number of). The one limit: a block may span at most 255 fine steps along an axis — a model past that falls back to centroids (points), and says why.

Rotated models

A model whose lattice axes aren't east/north/up — a deposit modelled along its strike — draws as true rotated boxes, with exact picking and true sections. When a model's centroids sit on a rotated lattice, micro finds it, and asks before applying it: rotated boxes, or points? An inferred rotation is never applied silently. A Parquet file can instead declare its lattice (written by micro, by an OMF project, or by any producer — App. D); a declared lattice is applied without asking, but checked against every centroid, and refused, loudly, if one falls off it.

On a rotated model everything that works record by record works — filters, stats, grade–tonnage, swath, the cross-tab, export, select, flag and proportions by solid or surface, model QA, block vs sample, grade shells — and joins and reconciles work between models on the same rotated lattice, a sub-blocked model onto its rotated parent included. A rotated model may be sub-blocked: by-geometry queries probe each sub-block in its own box. Not yet: resampling between different orientations (the join panel says so) and the empty-grid creator.

A Datamine .dm with one rotation (ANGLE1 about Z) is placed in world coordinates: ANGLE1 turns the model axes clockwise seen from above, about the origin X0/Y0/Z0 — or one you give in the open dialog or with Datamine origin… (an anonymised export carries none). Its XC/YC/ZC then read in world coordinates everywhere — filters, stats, swath, selection, the record panel (which also shows the model's own frame), export. A Parquet export carries the rotated lattice and reopens as rotated boxes. Two or three rotations stay in the model's own frame, with a warning. Datamine origin… is a shortcut to a placement: a shift that puts the model's local origin where you say.

Which format to keep a model in

A CSV is the most portable; a Datamine .dm opens instantly and reads one column at a time; a Parquet file is the smallest and the fastest to query — micro's own store, Morton-sorted so the filter skips whole stretches of the file it can prove don't match. Store as Parquet… (right-click the model) converts one; saving a project offers to do it for you. See the project store.

Model QA

Model QA… (right-click a block model, or ⌘K “model QA”) reads the whole model once and reports what a reviewer should see before anyone reports from it, errors first:

  • The lattice — two blocks in one cell, a centroid off the grid, and gaps inside a column (missing blocks between a column's lowest and highest block). Checked on regular models, axis-aligned or rotated (a rotated one in its own lattice frame).
  • Sub-blocks tile their parents — on a sub-blocked model, each parent's sub-blocks must fill it exactly: sub-blocks that overlap (with the volume counted twice), a sub-block that crosses its parent, one off its parent's lattice or off the fine lattice, a Datamine IJK that disagrees with the position (all errors), and a parent not filled by its sub-blocks (a warning — often deliberate, above the topography or outside a domain). The check streams parent by parent and never builds the fine grid: an 18.7-million-block model takes about four seconds.
  • Every column — blank values (an error for a coordinate), sentinel codes such as −99, −999 or −1e30 read as numbers, text in a numeric column, negative values, a constant or empty column.
  • Density (a column named DENSITY, SG, BD, …) — zeros, and anything outside 1–6 t/m³.
  • Top cut — a maximum more than ten times the 99.9th percentile.

Click a finding to select its blocks (then Selection → column, or the attribute table's selection view); a gap has no blocks to select, so a click steps the camera through examples. Below the findings is a census of every column (values, blanks, min, median, 99.9th percentile, max, mean). export .tsv saves both. Nothing in the model is changed.

Grade shells

Grade shell… (a block model's menu, or ⌘K “shell”) draws the surface around every block at or above a cutoff — contouring a volume — and adds it as a closed mesh layer: AU ≥ 0.8 shell. The surface passes between block centres where the grade crosses the cutoff, and closes on the block faces where the model ends or a block is missing, so a shell is always a solid. Smoothing (light / medium / strong) averages each block with its neighbours first; it is off by default, so the shell shows the blockiness the model has. Only the filtered blocks counts just the blocks matching the layer's filter as inside — a shell within one domain.

The shell is a solid like any wireframe: select, flag or measure the model against it (Select by solid), read its volume and tonnage in Mesh QA, export it as OBJ, PLY, DXF, .msh or .wfr. Its lineage records the column, cutoff and smoothing. Shells are built for regular models, axis-aligned or rotated (a rotated one is contoured in its own lattice frame); on a sub-blocked model the command says why it can't run.

10Drillholes

A drillhole set is three tables bound by the hole id — collars (one row per hole), survey (deviation stations), intervals (from/to samples) — and micro keeps that structure first-class rather than flattening it away.

The set in the layers panel

Every load lands as a set group: the group is the drillhole set, with a ◈ collars row (hole count), a ↧ survey row (desurvey method), and one interval layer per interval table. The rows are live — click one for its menu:

  • ◈ collars — Attribute table… (the collar file as a table), Filter holes…, Broadcast column to intervals.
  • ↧ survey — Attribute table…, Re-desurvey… (method: minimum curvature / balanced tangential / tangential; dip convention), Show hole traces (the full collar-to-EOH paths as thin grey sticks, filter-aware).
  • The set group itself — hole traces, Show collars, Add interval table… (assays + lithology + geotech share one geometry as sibling layers).

The hole filter — filter by collar data

Filter holes… takes an expression over the collar columns — EOH > 200, COMPANY = "ACME", a campaign year — and applies the verdict through the whole set: only the matching holes' intervals stay visible (in every interval table at once), the traces redraw for the matching holes only, and the interval filter box then works within the kept holes. Nothing is copied or materialized — it's a live mask driven by the hole relation, and it persists with the project.

Broadcast — collar data on the intervals

Broadcast column to intervals lands a collar column on every interval, matched by hole id — so EOH, the logging company, or a campaign field becomes a real interval column you can filter, color, and export by. Numeric columns materialize to the project's column store; text columns become category columns with a legend. The operation is recorded with its inputs, like every derivation.

Display

Intervals render as true cylinders (Stick radius… sets the world-space radius). Color by any interval column; sections cut the sticks true, and the set usually reads best with the model sectioned and the holes set to don't cut, threading whole through the opened deposit — which is exactly how the demo project arranges itself.

Keep holes that cross the slab. A drillhole layer's Cut by sections menu has one more mode: the holes aren't cut, but only the ones whose path, collar to end of hole, crosses the section's slab are drawn, whole; the rest are hidden. It's the path that counts, not the samples, so a hole that passes through the slab in an unsampled stretch still shows. It follows the section as you scrub, and works together with the interval filter and the hole filter. It only decides what's drawn, though: it isn't a filter. Exporting the filter's matches, Filter → selection, the analyses' filtered scope and the attribute table's matches still get every interval the filter matched, wherever the section happens to be. Holes test their own slab… makes the test band wider (or narrower) than the section's, so a ±5 m model section can show the holes within ±50 m.

Log tracks

A stick shows one column, as colour. View → Drillhole logs… (or ⌘K “drillhole logs”) gives every hole as many tracks as you want, each a ribbon running beside the hole interval by interval: a bar, whose width is the value on the track's scale (FE on the right, SG on the left), or a strip of constant width coloured by the value (LITO by its classes, a number through a ramp). Each track has a side — right, left, or centre on the trace — and a width and offset in metres, automatic when left blank. The sides are the screen's, so a right track stays on your right however the hole runs, and a section through a fan of holes reads like a sheet of logs. The tracks follow the hole filter, the layer's filter and the section, appear under the layer's legend in a figure, and are saved with the project.

Collars

Show collars on the set draws one glyph per hole at its collar, as a points layer nested in the set (holes · collars). It is the collar file itself, so every collar column — hole id, end of hole, campaign, rig, company — can colour it, filter it, and fill the record panel when you click a collar. The glyphs start at three times the point size; Point size in the layer's menu changes that. The hole filter thins them along with everything else in the set. They aren't saved as a layer of their own: the set remembers they were shown, with their size and colour, and a reopen brings them back (and the hole traces too, if they were on).

Blanks, and the QA report

A blank in a drillhole table is never read as zero. A collar with a blank X, Y, or Z is dropped (its intervals are kept as records but not placed); a survey station with a blank depth, azimuth, or dip is dropped and the hole interpolates across it; an interval with a blank FROM or TO stays a record but isn't placed; a blank end of hole falls back to the deepest station or interval. File info lists each kind, by hole. For every problem row by row — orphans, duplicates, doglegs, gaps, overlaps — see the drillhole QA report.

Composites

Composite… (a drillhole layer's menu, its set's menu, or ⌘K “composite”) re-cuts one interval table into equal lengths down each hole — the support samples go into an estimate with, and the fair way to compare them with a block model. Choose the length (blank takes the commonest interval length), the text columns to break at (a composite never straddles a change of domain or lithology; it restarts at the contact), an optional density column (grades are then weighted by length × density), and a min length % (drop composites whose sampled length is below that share of the composite length — the short leftovers at contacts and hole ends). Numbers are length-weighted means, ignoring missing assays rather than counting them as zero; text takes the value covering most of the composite.

The result is a new points layer, each composite at the centre of its sampled length on the desurveyed hole, carrying BHID, FROM, TO, SUPPORT (the length actually sampled) and every interval column. It filters, colours, exports and saves like any layer, and its lineage records how it was made. export .csv saves the table without adding a layer.

11Meshes, wireframes & CAD

micro opens surfaces and solids from the formats mine software writes: Leapfrog .msh and .lfm, .obj, .ply with faces, Datamine wireframe pairs, DXF, .wfr, and the surfaces of an OMF project. A mesh is a layer like any other: its own eye, tint, opacity, and section behaviour, and a sectioned mesh draws its trace on the cut face.

  • Multi-object files — a .obj or .lfm holding several objects offers split into N solids (as a group) when it opens; .lfm solids keep their Leapfrog colours.
  • Datamine wireframes arrive as a pair — a points file and a triangles file (…pt.dm / …tr.dm). Open both together and they become one mesh; a lone half says which half is missing.
  • Picking a mesh reports the point on its surface. A mesh's vertices are its records: the attribute table lists them, and a painted PLY's colours arrive as columns.
  • Big meshes can be held two ways: exact (every triangle on the page — needed for solid queries and mesh QA) or streamed (light on memory, display only). The layer menu converts between them and says what each costs.

DXF

A DXF opens by what it mostly holds: 3D faces and polyface meshes become a mesh; 3D polylines — design strings, pit crests, ramps — become a strings layer drawn as thin tubes and categorized by DXF layer, so the classes tab hides a bench or a toe line with one click; points become pegs. Open as ▾ in the open dialog, or Reinterpret as… on the layer, crosses between the three when the guess is wrong.

.wfr — compact wireframes

.wfr is an open wireframe format (gentropic.org/wireframe): many surfaces, strings, and point sets in one file, each named, with their attributes, in a fraction of the size of the text formats. File → Convert files to .wfr… converts mesh files (.ply .obj .dxf .msh .lfm, Datamine pairs) without loading them; Export as .wfr… writes loaded layers; Store meshes in the project as .wfr packs a project's meshes in place. The coordinate grid (0.1 mm by default) sets the precision, conversions stream with a memory budget, and verify topology checks the result.

OMF projects

An Open Mining Format v1 file (.omf — written by Leapfrog, Surpac, Vulcan, Deswik, Micromine) opens as one layer per element, in a group named after the file. A block model becomes a block layer with its lattice declared (rotated axes kept) and checked against every block; uneven block widths open as centroids. Point sets become points; triangulated surfaces become meshes. Scalar data become numeric columns and mapped data a text column from its legend. The open dialog lists what a file holds before you open it.

Note — Not read yet, and named on the status line when a file has them: line sets, gridded surfaces, vector and date data, textures, and data on surfaces.

Mesh export

Export mesh… (right-click a mesh layer; multi-selections and groups get Export N meshes…) writes OBJ, PLY, MSH (Leapfrog/ARANZ), or LFM. OBJ and LFM are multi-mesh — one named object per layer, with each layer's tint carried as the LFM colour — while PLY and MSH merge several layers into one mesh. Exports re-read the source geometry, so coordinates leave in full double precision (the PLY writer uses double — at UTM northings, float32 would cost half a metre). A Datamine wireframe pair in, an LFM out: micro is also a mesh-format converter.

Tip — Before a wireframe bounds anything, check it: Mesh QA / volume… on its menu — see Mesh QA.

12Strings & polygons

Pit limits, lease boundaries, blast outlines and mapped contacts open as a strings & polygons layer: lines and closed polygons in 3D, whose records are the features. Each feature carries its attributes, so the layer is a table like any other — the attribute table lists one row per feature, the filter keeps whole features (BENCH >= 850 and STATUS = "approved"), the colour list colours by any column, and a click on a line shows that feature's record. Holes and multipart features are kept.

  • What opens — a CSV string file (an ID column such as STRING or LINE and one row per vertex, the way Leapfrog and Surpac export polylines; a string that returns to its first vertex is a polygon), WKT and WKT-CSV (a wkt_geom column — QGIS's shape), a shapefile (.shp + .dbf + .prj + .cpg selected together, or zipped), GeoJSON, KML / KMZ, and a DXF through Open as ▾ → strings & polygons. A feature with no Z is drawn at z = 0 and the status line says so; Geometry → Set elevation… places the layer at a bench.
  • QGIS and the clipboard — copy features in QGIS and press Ctrl+V over micro's view (or File → Paste features (WKT from QGIS)): they arrive as a new layer, attributes as columns, and features digitized in 2D ask for an elevation — micro never guesses a Z. The other way, Data & file → Copy features (WKT, for QGIS), then Paste Features As → Temporary Scratch Layer in QGIS.
  • Display — Display → Fill polygons shades each inside (holes left open; the fill is never picked, so a click reaches what is behind), Classes by… makes any text column the category, Line width… sets the tubes' half-width.

Drawing and editing

Tools → Draw polygon… and Draw line… draw over whatever is open; look from above first (d). Click to add a vertex — it snaps to an existing feature vertex within ten pixels, Alt places it freely — and close on the first vertex, with a double-click or Enter; Backspace takes a vertex back. micro then asks for a name and optional key=value attributes (code=B12, bench=850). Geometry → Edit vertices puts a handle on every vertex and edge midpoint: drag to move, drag a midpoint to add, Alt-click or Delete to remove — each edit one undo step. A drawn or edited layer is saved as WKT-CSV in the project's polygons/ folder; editing a layer opened from a shapefile never changes that file.

A polygon as a limit

Any analysis can be limited to what lies inside polygons in plan: the tonnes inside the pit limit, the cut and fill inside a stockpile toe, a DEM of the lease only. Grade–tonnage, swath, stats, contact analysis and the factors have an inside row under the scope (cut and fill calls it perimeter; the point-cloud DEM and the projection to grid have it in their dialogs): pick the layer, then all polygons, one feature, or the ones selected in 3D. It adds to the scope — filt and inside pit keep the filtered blocks inside the pit. A record counts by its plan position, a block by its centroid; a grid node counts by the exact share of its cell inside the outline, so a volume inside a perimeter is exact at the edges. In a routine the setting is limit: { layer, feature, where }, recorded in the lineage.

Extruding to a solid

Tools → Extrude polygons to a solid… turns polygons into a closed solid that every by-solid tool takes (select, flag, fraction, assign domains, the factors): between two levels (a blast from floor to crest), along a direction (a trend and plunge for a length), or between two surfaces (walls on the outline, caps following a grid or mesh, refined within a tolerance). one per polygon makes a layer per feature, as assign domains wants. Every solid is checked watertight before it opens. On a regular model, a between-two-levels prism's fraction inside is exact, not sampled. Routine tool extrude.

Section lines and bench outlines

Tools → Section lines → strings… keeps where a plane cuts meshes, gridded surfaces, or a block model's domain boundaries (Geometry → Domain boundaries on a section → strings… on a model) as features in world coordinates — a pit shell cut on a plan gives the bench toe, a lithology model on a cross-section the ore/waste contact, ready for CAD as DXF or a shapefile. The plane is the current section or one you state, and series cuts several positions into one layer. Domain lines follow the block faces exactly (a staircase, not a smoothed contour), each naming its two domains; a closed line on a plan becomes a polygon, so a bench toe can serve as a limit. Routine tool sectionlines.

Tools → Bench outlines → polygons… traces the plan outline of a set of blocks bench by bench — the drill-and-blast dig line. Choose the blocks (all, filtered, selected, plus an expression such as FE >= 60) and what is outlined (all as one, each category value on its own, or one value). The tracing runs on the model's own lattice, so every vertex lies on a block corner; holes are kept, two blocks touching at a corner make two polygons, and simplify drops corners within a tolerance. Each polygon carries its bench, levels, block count, area, volume and — given a density — tonnes. Routine tool blockoutlines.

Exporting

Data & file → Export features… writes the layer (or its selection) with every attribute as WKT-CSV, GeoJSON (with a "crs"), a shapefile zip, or DXF (a polyline per ring, on a DXF layer named by the category, attributes in extended data micro reads back). A shapefile carries a .prj: the one the layer came with, or one written for the project's system; two more formats export in WGS 84 degrees — see Coordinate systems. All of them open again in micro with the same features, attributes and coordinates.

In the book — chapter “Strings and polygons”, in the full manual.

13Coordinate systems & placements

Survey pickups arrive in SIRGAS 2000, an old lease map in SAD69, a GPS track in WGS 84 longitude and latitude, the block model in the mine's UTM zone. micro keeps one coordinate system for the project and brings everything into it as it opens — saying each time how, and how far the result can be trusted.

The project's system

The CRS chip at the right of the status bar, beside Sealed, shows the project's system — EPSG:31983, or no CRS; a click opens the selector (also File → Coordinate system…, ⌘K “coordinate system”). The first vector file or point cloud that states a projected system sets it if the project has none; otherwise pick one or paste an EPSG code, a proj4 string or a WKT (a .prj's contents). It must be projected — micro works in metres — and it is saved in project.json.

The selector carries the whole EPSG table — 6,983 systems with names and areas of use — inside micro.html; nothing is fetched. Search by words in any order (sirgas utm 23s) or by code, filter to fits my data, take a suggested system for where the data sits, and check it on the world map: the system's area of use in amber, your data's extent in violet. An ESRI .prj without a code is matched by name.

Reprojection on read

Strings and polygons in every format micro reads (KML and KMZ included), and LAS point clouds whose coordinate-system record names another system, are reprojected as they open. The file's system is its .prj, SRID or "crs"; GeoJSON without one and KML are WGS 84 longitude and latitude, as are unlabelled coordinates that all fit within ±180 / ±90; an unlabelled file in metres is taken to be in the project's system already. The move is horizontal — elevations are carried unchanged. A longitude/latitude file opened while the project has no system is refused, with an offer to set one: micro never places degrees on a metre grid.

Every reprojected layer records the path its coordinates took — in its source tab, file info, lineage and the open dialog — with an accuracy class: exact (same datum, projection maths only), sub-metre (WGS 84 / SIRGAS 2000 / ETRS89-class frames taken as identical), metre (a Helmert datum shift, with its source — for SAD69 and Córrego Alegre in Brazil, IBGE's R.PR 1/2005 parameters), grid (an NTv2 grid; none is bundled), or unknown (no shift applied — possibly tens to hundreds of metres out).

Placements — models, grids and meshes in a frame of their own

Block models, grids and meshes are not reprojected: moving each vertex would bend a model's boxes. A model in the mine's local grid, a drone mesh in its own arbitrary frame, an anonymised export about (0, 0, 0) takes a placement instead: one rigid similarity for the whole layer — a shift, three rotations and one uniform scale, never a shear — applied as the layer is read, so picks, analyses, sections, exports and lineage all see the placed coordinates. The file is never rewritten. Open it with Data & file → Placement… (or ⌘K “placement”), in three ways:

  • typed — the shift, rotations ω φ κ about X, Y, Z, a scale and a pivot (pivot = the layer's centre turns it in place);
  • control points — pairs of local and true coordinates, typed, picked on the layer in the 3D view, or pasted as a table; two pairs fix a 2D fit (shift, turn, scale — a mine grid on UTM), three or more with heights a full 3D one. Every pair shows its residual, green, amber or red against a tolerance; untick a bad pair and it still says how far off it is. While the tab is open the pairs are drawn in the view — a ring at the local point, a square at the true one, a line between them in the residual's colour;
  • CRS change — the layer's own system: micro samples the true reprojection through the layer's extent, fits the best similarity, and states the maximum deviation from it (a datum shift within one zone: a fraction of a millimetre; a change of UTM zone over five kilometres: centimetres — read the number before trusting it).

A large residual is never refused — it is shown, in the window, the source tab, the status line and the lineage. Georeferencing a drone outcrop is the control-points tab with three or more surveyed targets picked on the mesh; once applied, structural measurements on it are refitted with true dip directions (see Structure). Drillholes and strings don't take a placement: their coordinates are survey data, reprojected on read. A grid shown as a surface takes a rotation about Z only. Store as Parquet bakes the placement into the new file.

Checking collars against the topography

A collar CSV doesn't say which system its coordinates are in, and in Brazil SAD69 or Córrego Alegre coordinates sit 60–70 m from SIRGAS 2000 in the same UTM zone — enough to put every hole on the wrong bench and still look plausible. The topography gives it away: Analyse → Check CRS against topography… on a drillhole set reads the collars as the project's system and as each datum twin (same projection and zone, another datum), samples each reading on the DEM, and ranks them by the median |Δz|, with spread, the share within tolerance and how far each reading moves the collars. The verdict is a sentence — collars fit the topography 17× better as SAD69 / UTM zone 23S … — and nothing changes until you press reproject the collars as … (undoable). On flat ground it refuses to name a datum, and a constant vertical offset everywhere is reported as such.

Exporting, and captions

A strings & polygons layer also exports in WGS 84 degrees: KML for Google Earth and a GPS, and GeoJSON in lon/lat. A shapefile carries the .prj of the system its coordinates are in now — the file's own, word for word, or an ESRI-style one written for the project's system with the EPSG code inside (written for the common projections; otherwise the status line says which system to set). In the composer, {crs} prints the project's system, {crs:name} and {crs:code} its halves.

14Grids & surfaces

GeoTIFF / Surfer .grd / ESRI .asc open as heightfield layers — an elevation point cloud where cells are pickable records (huge DEMs decimate for display while the full grid stays for evaluation). A mesh right-click → Rasterize to grid… renders it onto a DEM (the surface↔grid converter, with fill / extrapolation for gaps). New… → grid / block model creates empty grids from parameters, covering a layer's bounds, or — cover compatible models — on a lattice that covers and is compatible with several models at once (the reconcile target).

Rotated grids. A GeoTIFF whose georeference rotates the raster, or one opened together with a world file (.tfw, .wld) that does, keeps its nodes on its own lattice and is placed rotated in the world, like a rotated block model; the status line says rotated 30°. Everything that reads a grid reads a rotated one in its own frame.

Export grid… (a grid's Data & file menu, or ⌘K “export grid”) always writes the full-resolution grid, never the thinned display, as ESRI ASCII, a float32 GeoTIFF (with the provenance in its description, and a CRS only when micro knows its EPSG code), Surfer 7 or 6 binary, Surfer 6 ASCII, ESRI binary float (zipped with its header), or an XYZ / CSV of nodes. A rotated grid keeps its rotation in GeoTIFF and XYZ; the formats with no rotation terms refuse it unless you tick resample to axis-aligned. Routine tool gridexport.

Show a grid as a surface — relief, flat, and draped

Right-click a grid → Reinterpret as → surface renders it as a solid, smooth-shaded relief mesh — a DEM reads as terrain, not a gappy point cloud. In Properties → Style a surface then offers:

  • Drape — color it by its own elevation/value, or by another loaded grid's values (grade / geochem / slope over topo), sampled at each point. Paint the terrain with whatever channel you like. (The drape source is a 2D grid, sampled by position.)
  • Shape → flatten @ z — turn a 2D data grid that has no elevation (a grade or geochem grid) into a horizontal colored sheet at a chosen level, colored by its value. A plan sheet, floating where you put it.
  • Band — for a multi-band GeoTIFF, a picker to choose which band is shown (a GeoTIFF's bands are like a grid's columns). Switch it anytime; it re-reads that sample.

Surface, drape, flat, and band all persist in the project — reopen and the terrain comes back exactly as you left it. Sectioned surfaces draw their trace on the cut face (see Sections), and layer opacity applies — a translucent topo over an opened pit.

Surface tools: extend & combine

Extend to footprint… (right-click a surface — mesh or grid) grows it to cover a chosen extent: nearest holds the boundary z flat (the "extend the outer ring" move), trend continues the fitted dip. A topo that stops short of the model no longer leaves blocks unclassified — extend it, then flag above/below covers everything. Combine surfaces… rasterizes two or more surfaces onto one lattice and resolves the overlap by a rule: min (topo ∧ weathering base — take the lower), max, first (list order is priority — patch an end-of-month survey into the original topo), or mean. Both produce grid layers — exact and fast for flags and reconcile — with the rule recorded in the layer name and its lineage; export them anytime.

As-built: from a point cloud to a DEM

A drone flight or a laser scan of the pit is tens of millions of measured heights. Geometry → Grid points to DEM… on a points layer (LAS, PLY, XYZ, a CSV of points), or ⌘K “grid points”, turns it into a grid: a lattice over the cloud's extent at a cell size (or match: an existing grid's nodes), and per node a statistic of the points in its cell — min Z (the ground under vegetation), mean, max, or count. only keeps the points an expression keeps (Classification == 2, a LAS file's ground class), inside limits it to polygons, and empties leaves unsurveyed nodes blank or fills them (nearest or planar trend, optionally holes only). The cloud is read once and never held: 10 million points grid onto a 1 m lattice in about two and a half seconds.

Tip — Put the nodes on round multiples of the cell (the default) and every survey gridded at that cell lands on the same nodes, so this month's DEM and last month's subtract node for node with nothing interpolated. A blank node means not surveyed — think twice before filling past the pit crest.

Cut and fill

Tools → Cut / fill between surfaces… (or ⌘K “cut fill”) gives the volume moved between two surfaces of the same ground — last month's survey and this month's, the pre-mining topography and today's pit. Pick before and after (grids or exact meshes) and Run: both are sampled on one lattice, and the readout gives cut, fill, net in m³ and the area both cover; nodes blank in either surface sit out. The chart is the volume in each band of Δz — cut in red, fill in blue — and Δz layer keeps the difference as a grid on a diverging ramp. A perimeter limits it to polygons, exact at the edges. Routine tool cutfill, whose values a check can gate on. For tonnes and grade between the surveys, give the same surveys to the reconciliation factors.

15Tables & spreadsheets

Not everything in a project is spatial. Drop a CSV with no X/Y/Z columns — a cut-off table, a density lookup, a price deck, a routine's parameter table, a report you exported earlier — and micro opens it as a table layer: rows and columns, no geometry. It sits in the layers panel with a ▦ mark instead of an eye (there is nothing to show or hide), and it never enters the 3D budget.

Everything that is about data works on it: the attribute table, the filter (the same expression language — the matches drive the table view and the export), ƒ calc columns, stats, and Export rows. Everything that is about space is simply not offered — no grade–tonnage, no swath — because there are no coordinates to work with, not because a rule forbids it. Table files live in tables/ in the project folder and reopen as tables.

A spatial layer can be reinterpreted as a table (drop the geometry) from its context menu, and a table whose file does carry coordinates can go the other way. Before this, a coordinate-less CSV was simply an error.

Excel workbooks

Open an .xlsx and micro reads it with no import step: pick which sheets you want (or take the whole workbook, which arrives as a group named after the file) and each sheet becomes a table layer. Column types come from Excel itself — a number is a number, a date is a date — so nothing is re-guessed from text.

A workbook is not a coordinate system. A sheet whose columns happen to be called X, Y and Z might be a block model, or it might be a table about something else entirely, so micro never assumes: every sheet opens as a table, and promoting one to geometry is your explicit act — Reinterpret as → block model / points, offered only when the columns actually support it. The workbook stays the layer's source file, so the project remembers which sheet a layer came from and re-reads it on load.

This makes the spreadsheet a first-class citizen of a project: keep the quarter's run matrix, cut-off tables, or density lookups where they were already maintained. A routine can read its parameter table straight from one — from: "params.xlsx#Bench targets" — so you can edit the workbook in Excel, Reload from disk, and run the routine again without leaving micro.

16Selection & domaining

Select with r (rectangle) or v (lasso): what you see gets selected (occlusion-honest, all visible layers), tinted gold — shift adds, alt subtracts, Esc clears. A plain release puts the tool down (left-drag orbits again); release with shift or alt held and the tool stays armed for the next gesture — you're clearly accumulating. Middle-drag orbits and right-drag pans either way, so navigation never leaves; Settings → interaction offers one-shot and always-armed instead. The select-through toolbar toggle flips to the extruded tube: everything whose position falls inside the shape, occluded included.

Select by solid / surface (Tools menu, or right-click a mesh) classifies records against a closed mesh by winding number: select inside/outside, write a flag column, or a fraction-inside 0–1 column. Open surfaces (topo, weathering horizons) classify above / below / between. Assign domains runs the whole coded-model loop — pick the domain solids and a column name, and every block goes to the solid holding its largest fraction.

The whole evaluation is recipe-able: save as recipe… in the dialog captures geometry, mode, engine, targets, and the column — so “flag the oxide onto this month's model” is a saved file that re-runs from Tools → Recipes or as a routine step, layers resolved by name.

Paint a column (b) is interactive domaining by hand: a category column you fill by brushing over the scene. Painted values are real columns the filter, table, and export all see.

Selection → column… (right-click the layer, or the palette) materializes the current selection as an explicit 0/1 column — every row gets a value, so it filters (SEL = 1), edits like any painted column, and rides every export. Selections themselves also persist in the project.

Analysis

17How the analysis windows work

Grade–tonnage, the cross-tab, swath, stats, scatter / Q-Q, contact analysis, validation and the reconciliation factors share one design, so learning one teaches them all. Each is on a layer's right-click Analyse menu and in the palette, which lists only what applies to the active layer.

  • A rail and a plot. Settings on the left, the result on the right. Configure, then Run: one streamed pass over the data. While it runs the button cancels it; the previous result stays until a new one replaces it.
  • Display is free after Run. Cutoff counts, units, bands, axis ranges, measures, flips — whatever a window can change without re-reading the data, it changes instantly. A setting that needs a new pass marks the window config changed — Run to update.
  • Scope: all · filt · sel. all is every record; filt follows the layer's filter box — type LITO = "HEMATITE" and every window scoped to it re-runs; sel follows the 3D selection — rubber-band a bench, a domain, or a suspect zone and the result recomputes for just those blocks, live, as you brush. That is linked brushing: the analysis becomes regional exploration, not a whole-model summary. Under the scope, an inside row limits the pass to polygons in plan, on top of the scope.
  • Where it runs. On a Parquet, .dm, or indexed CSV model the pass runs in background workers, reading only the columns it needs; elsewhere it runs on the page, a slice at a time, and the window stays responsive either way.
  • The results row. Every window's footer has the same actions in the same place: ⤓ png and ⧉ copy for the plot, ⇥ figure to send the plot and its table to the composer page as a vector chart that remembers the analysis behind it, ⇥ layer to keep the result as a table layer (filter it, join it against another run), ⧉ table to copy the numbers as TSV for a spreadsheet.
  • Recipes. save as recipe… writes the setup as a re-runnable YAML file — see Recipes.
  • Saved with the project. Every setting is snapshotted on each Run and on close, and a window left open when you save is pinned: reopening the project brings it back in place, configured, reading restored — Run to compute. Run stays manual, so a huge project never surprise-scans on open.

Units are declarations. Where a window takes a grade unit (%, g/t, ppm, oz/t) or a density unit (t/m³, kg/m³, lb/ft³), you are stating what the data is, not choosing a display: series convert onto a shared axis honestly, tonnage is in tonnes, and metal comes out in tonnes when the grade unit is set. Density is a free expression — SG, 2.7, SG * PARTIAL — and tonnage is density × block volume, each sub-block weighted by its own size.

18Grade–tonnage

Grade-tonnage… (right-click a model, or the palette) draws tonnage and mean grade above cutoff. It shares the swath's interface: a config rail of series, each one a layer + grade column + declared unit + density expression + optional row filter — configure, then Run. Because series pick their own layer, model-vs-model curves (this estimate against the last one) are one window; on a reconcile layer the reference/new pair is pre-seeded. Derived columns — calculated, materialized, joined — are all offerable as the grade or the density.

  • Density is a free expression (SG, 2.7, SG * PARTIAL) — tonnage = density × block volume, with a declared density unit converted to t/m³ so tonnes are tonnes. Blank = count/volume.
  • Units are declarations, not display toggles: declare what each series' grade is (%, g/t, ppm, oz/t) and a plot unit — series convert onto the shared axis honestly, so a %-model overlays a ppm-sample set without lying.
  • One streamed scan per Run caches each series' cumulative curve, so cutoff count, plot unit, and manual axis ranges are live afterwards — no re-scan.
  • ⤓ png saves the plot, ⧉ copy puts it on the clipboard, and ⧉ table copies the numbers as TSV — cutoff · tonnes · grade · contained metal per series, ready for a spreadsheet.

19Resource cross-tab

Resource cross-tab… (right-click a block model, or the palette) tabulates the model the way a resource table is laid out: a group down the side — a category or painted column, so domains or classes — and grade bins across, between the cutoffs you type, with a total row and a total column. It is a checking table, not a resource statement: micro tabulates what the model holds; classifying and reporting a resource is the estimator's job.

  • Cutoffs — typed ascending, 0.5 1 2 (a comma is a decimal comma when the values are space-separated: 0,5 1 2). Empty gives one graded column.
  • Measure — tonnage, mean grade, metal, or block count; switch freely after a Run.
  • between · ≥ cutoff — bins between consecutive cutoffs, or cumulative above each, the grade–tonnage reading of the same numbers.
  • ⇄ flip — rows and columns swap.
  • No grade — a block with a blank grade keeps its tonnage in its own column, never silently dropped, so the table adds up to the model.
  • ⧉ table copies every measure in long form — group · bin · tonnage · grade · metal · blocks — ready to pivot in a spreadsheet.

The resource table on a page. When the numbers are settled, the composer's Add resource table builds the table most reports are written around: tonnes, grade and metal above a list of cutoffs, by up to two category columns (domain, then class), always cumulative, with a note stating the density, the filter and the records read. A declared grade unit gives the metal factor (% → 0.01, so metal in tonnes), or state one such as 1/31.1035 for troy ounces. It remembers its settings, so the composer's Refresh makes it again from the current model.

20Swath / drift

Swath plot… shows mean grade per band along a direction — the classic drift check for local bias. The direction can be the grid axes X/Y/Z, an oriented trio from dip-direction / dip / rake (across-structure · along-strike · down-dip), or a single trend / plunge. Series work exactly like grade–tonnage's: layer + column + declared unit + a free weight expression (blank = block volume) + an optional per-series row filter — so kriging vs nearest-neighbour vs declustered samples overlay in one plot.

One Run streams everything once into fine bins; after that, band width and offset re-bin instantly — and they are per direction, so your E–W drift keeps its 25 m bands while the bench-by-bench Z profile keeps 10 m. Manual axis ranges, ⤓ png / ⧉ copy / ⧉ table (band · count · weight · per-series mean, TSV) match grade–tonnage.

Zebra paints the alternate bands onto the 3D, so the slabs you see in space are the bins in the plot.

The band ghost — hover the plot, see the slab

With locate on 3D on (it is by default), hovering the swath plot lights that band on the 3D as a translucent slab outline — so a dip in the profile points straight at the benches or the zone that caused it. Drag across the plot to hold a band range (violet), then turn it into a real 3D selection right from the menu that appears — and from there it's linked brushing, a 0/1 column, or an export like any other selection.

21Stats, scatter & Q-Q

The stats table

Stats… (right-click a layer, or the palette) is the grouped summary: pick columns, an optional group by (the category channel or any painted column — assign domains, then stats by domain), and an optional weight expression (SG for density-weighted means — quantiles stay unweighted and the window says so).

Scatter

Scatter / Q-Q… (right-click a layer, or the palette's Scatter plot) plots one column against another, with an optional filter and the usual scope. While there are 20,000 pairs or fewer, every pair is drawn as a point; past that the plot is a density of counts on a fine grid (log-scaled, so the sparse tail stays visible) — so it works the same on a 60-million-block model. log x / log y suit skewed grades; a value ≤ 0 can't sit on a log axis, so it is counted and the note under the plot says how many were left off. The note also gives n and the correlation r on the axes as drawn. 1:1 line is for two grades in the same unit.

Q-Q

The Q-Q tab compares two distributions, quantile against quantile. Each side is its own layer, column, filter, and scope, so the classic checks are one window: the model against the drillholes, this estimate against the last, one domain against another. Points on the dashed 1:1 line mean the two distributions agree there; dots mark P10, P25, P50, P75, and P90, and the note gives the P10 / P50 / P90 ratios.

Note — Quantiles are unweighted, and the window says so. Drillhole intervals of different lengths, or clustered drilling, weigh the sample side; for a declustered comparison of the means, and model-vs-sample swaths, use Validate.

22Contact analysis

Every domain has a boundary, and every boundary asks: does the grade jump across it, or change gradually? Before the estimate, the answer decides whether each domain is estimated with its own samples only; after it, whether the model kept the boundary the way the samples have it. A contact plot answers both: mean grade in bins of distance from the boundary, negative on one side, positive on the other. A hard boundary is a step at zero with flat sides; a soft one is a ramp, and the ramp's width is how far its influence reaches. The bin width is part of the reading — choose it near the scale of your blocks or composites.

  • Contact plot… (a drillhole layer's Analyse menu, or ⌘K “contact”) finds the boundaries in the logging: every place a hole passes from domain A to domain B in a column you name (a lithology, a painted or ƒ column, a numeric code), measured down the hole — pooled, or A above B, or A below B.
  • Distance to a surface… (on a drillhole layer or a block model) measures every record's signed distance to a wireframe: to the nearest point of a closed solid (inside is negative) or an open surface (below is negative), or vertically to a gridded surface. Its series can mix samples and the model on one chart, against the same surface: if the samples step and the model ramps, the estimate has smeared grade across a boundary its data call hard.

The readout gives each series' weighted mean just inside and just outside, and the step between them (a second series' step also as a percentage of the first's). Read the counts before the curve: the far bins hold fewer metres. In the surface flavour, ⇥ column writes every record's signed distance as a stored column — abs(DIST_ORE_SHELL) < 10 is then a filter for the contact zone. The window is built on the shared chassis (rail, Run, scopes, an inside limit, the results row, recipes), and the routine tool is contact, whose values a check can gate on.

23Join & reconcile

Two model versions, or a lookup table? The join tab (Properties → join) brings data across — and it follows one rule: if the operation keeps this layer's records, the result lands as columns on it; only an operation that changes the record set makes a new layer.

Only the 3D selection — a toggle above the run buttons scopes any join or reconcile to the rubber-banded zone: lasso the pit area, reconcile just it. Each side uses its own selection where it has one, and a scoped run is stamped selection: true in the lineage.

  • Key join → columns here — match rows by a key column (a block id, a domain code) and the brought columns land on this layer: numeric as materialized columns, text as categories, name collisions prefixed. The classic domain→density lookup is one join, no new layer.
  • Spatial join → columns here — with the target grid set to this model's own lattice, the other model's columns resample onto your existing cells (mean / sum / count, optionally weighted; categories by majority) and land as columns. A compatibility banner tells you whether the grids share a lattice, or why not.
  • → new layer — the secondary, export-shaped verb: a joined copy as a new layer/file. Spatial joins onto a third lattice (common-finest / coarsest) stay layers — they genuinely change the record set.

Reconcile is the preset: it produces a colored Δ map (this model − reference) on a common lattice, with a diverging ramp centered on zero — blue where the new estimate is lower, red where it's higher. The summary reads matched · mean Δ · mean|Δ| · added · removed.

Sub-blocked models reconcile by volume: each variable-size block is aggregated onto the reference (parent) grid weighted by the space it fills, so a sub-blocked estimate compares cleanly against a regular one at the parent resolution.

Tip — The Δ ramp auto-clips to the full range, which extreme blocks can widen. Tighten the min/max boxes (e.g. ±2× the mean|Δ|) to make the local pattern read, as above.

A comparison report

Reconcile shows where a model changed. The month-end question is wider: how many tonnes, how much grade and metal moved, in which domain and class, and from which version of which file. Right-click the new model → Analyse → Compare model versions… (also in the palette, the Tools menu, and the composer's comparison report…). Name the old and new models (a banner says how they map, or why they can't), each side's grade (two versions may spell it apart), a unit or metal factor, a density, up to two grouping columns and one or more cutoffs, then Make the page. A composer page opens with a comparison table (old and new tonnes, grade and metal per cutoff and group, with the changes), a map of the changed blocks (a Δ layer with a change column: added · removed · changed · unchanged), the biggest moves as caption fields, and both models' lineage with their content hashes. The table needs no common lattice; the map does. Refresh makes the whole page again next month.

24Reconciliation factors

At a month-end close the question is not where two models differ but whether the totals agree inside the volume that was actually mined. The resource model promised so many tonnes at such a grade, grade control found something else, the mill weighed and assayed what it received. The factors are the ratios between those three totals, per period: F1 = grade control ÷ resource model, F2 = mill ÷ grade control, F3 = mill ÷ resource model = F1 × F2 — each for tonnes, grade and metal. A tonnage factor above 1 with a grade factor below it is the familiar signature of dilution; reading the three together is the point.

Right-click the resource model → Analyse → Reconciliation factors… (or ⌘K “factors”). The rail has five sections:

  • models — the resource model and grade control, each a layer, a grade with its declared unit, and a density. The two may sit on any lattices (only totals are compared), and grade control may be other columns of the same layer (FE and FE_GC).
  • mined volume · periods — how micro knows what was mined when: a period column on the blocks; a solid / surface per period (inside or outside a solid, above or below a surface; nested for pit phases, so each period is the difference); surveys — the month-end pit surfaces in date order, the first one the starting ground, each later one closing a period; a filter; or the 3D selection. With volumes a block counts by the fraction of it on the mined side. An optional domain filter applies to both models.
  • production (mill) — a table layer with period, tonnes and a grade and/or metal, matched to the periods by name (several rows for one period are summed). Without one, F1 alone.
  • report — a cutoff (each model judged by its own grade), the report unit, the metal factor, and the tolerance band about 1.0 past which a factor is marked.
  • chart — which factors to draw, period by period or cumulative (to date).

A period's grade is never averaged from other grades: each source keeps tonnes and metal, and its grade follows, so to-date grades are true tonnage-weighted ones and metal = tonnes × grade and F3 = F1 × F2 hold exactly — micro checks both identities on every run. A missing ratio is blank, never infinity. The window has the shared rail, Run, ranges, results row and recipes, but no scopes: the mined volume is the scope. Routine tool factors, made for gating a month-end on its values.

25Structure on an outcrop mesh

A drone gives you an outcrop or a pit wall as a mesh of millions of triangles in real coordinates, and every joint face on it is an orientation measurement waiting to be taken — including the ones no one can reach with a compass. Right-click a mesh → Analyse → Structural analysis… (or ⌘K “structural”). A streamed mesh offers to load exact first; the first time, micro prepares the mesh (topology, vertex normals) once.

You paint the patch of mesh that is one joint face, into a set (J1, J2, bedding…), and micro fits a plane through the painted vertices by total least squares — a fit to where the rock is, area-weighted, so the roughness of a photogrammetric surface averages out. Each plane reports dip direction / dip (270/60), its size, its flatness e₂/e₁ and Fisher's κ, and a quality flag when it is rough, elongated (strike sure, dip much less), few vertices, or a straight trace. Nothing else is stored: the planes are measured again from the paint, so the table never disagrees with the rock.

  • wand — one click takes the whole face, walking outward until the surface turns away by more than an angle (12° by default); brush paints along a stroke without bleeding round an edge (⇧ wheel resizes it); erase unpaints. With the mouse at rest micro previews what a click would take and its attitude, before you commit. Every paint step is one undo.
  • trace — click along a fracture that shows only as a line; the trace follows the mesh surface and yields a plane where it crosses relief. Several traces form a network, with its I, Y and X nodes counted.
  • ◎ stereonet — the poles on a lower-hemisphere equal-area net, each set's Fisher mean and α95 cone, density contours. Lasso a cluster of poles and move it to a set: paint every face into one set, then sort them on the net.
  • ⇩ sets from paint — a mesh painted the ply2atti way, one pure colour per set, becomes sets directly; photographic colour never does.

→ table layer makes the planes a table (attitude, centre, the unit normal pointing out of the rock, fit statistics, quality) to filter and export; ⇥ figure sends the stereonet or the table to the composer, where Refresh re-measures from the current paint; ⇥ traces .dxf writes the traces as 3D polylines. The paint is saved with the project as a SET column on the mesh's vertices. To work in true coordinates, georeference the mesh first.

  • values — the second tab is a census of every interval column: blanks, numbers, below / above detection, lab codes, text.
  • export TSV writes every finding, under a header that names the files and their sizes, the limits, and the build — the report a reviewer can file.

A collar that can't be placed is reported once, at its own row; its surveys and intervals aren't reported again as orphans. Nothing in the report changes a table.

27Validate vs drillholes

Is the model consistent with the samples it was built from? Validate vs drillholes… (in the palette, with a block model active and a drillhole set loaded) takes a block model and a drillhole layer, declusters the sample grades (spatial sampling over-drills high grade, so a naïve sample mean is inflated), and reports the global bias (model mean vs declustered sample mean) plus a model-vs-sample swath along X/Y/Z.

Note — Samples are point support, blocks are block support, so a global grade offset between them can be real (change of support), not an error. The swaths are what flag local, conditional bias.

Block vs sample

Block vs sample… (a block model's menu, or ⌘K) pairs every sample with the block it falls in — the most direct check that an estimate honours its data. The samples are any points layer (composites, a sample file) or a drillhole layer (each interval at its midpoint). Pick the samples' column, the model's column and, optionally, a domain column of the model to split by. The window plots the pairs as a scatter or a Q–Q plot (log axes on request) with the 1:1 line, and tabulates, overall and per domain: the pairs, both means, the bias of the blocks against the samples, the correlation r, and the slope of block on sample — below 1 the estimate is smoother than its data (conditional bias). A bias beyond ±10 % or a slope outside 0.8–1.2 is highlighted. Samples outside the model, in a missing block or without a value are counted, not paired. select the disagreeing samples marks, on the samples' layer, those whose block differs by more than a factor you choose. A rotated model looks each sample up in its own lattice frame; a sub-blocked model isn't paired yet, and the window says so.

Tip — Composite the drillholes first (see Composites) so samples and blocks are compared at a like support.

28Mesh QA & volume

Mesh QA / volume… (right-click a mesh, or the palette) answers what you ask of a wireframe before it bounds an estimate: is it a solid, is it one piece, do its faces agree, and what does it hold.

  • Watertight — every edge shared by exactly two triangles. An edge on one triangle is a hole; an edge on three or more is non-manifold (a fin, or two shells touching along a line).
  • Faces one way — two triangles sharing an edge must cross it in opposite directions; when they don't, one of them is flipped.
  • Slivers and duplicates — zero-area triangles, and the same triangle twice.
  • Shells — the separate pieces, each with its triangle count, whether it is closed, its volume and area, and its size. Click one to frame it.
  • Volume — of each closed shell, in the coordinates' units cubed. A shell wound inward has a negative volume, which is how a void inside a solid subtracts; the total is the signed sum. Type a density for tonnes.

Click an issue to step the camera through where it occurs. Coincident vertices are welded first — a per-face mesh from some CAD exports shares no edge otherwise, and would read as a pile of loose triangles; untick it to see the file as it is. ⧉ table copies the shells.

Note — Self-intersections (faces crossing without sharing an edge) aren't checked yet. A mesh held streamed keeps no triangles on the page; convert it to exact first.

Every derived layer and every derived column remembers how it was made. Opening a file is a leaf; a join, reconcile, or optimize wraps its source layers with the operation, its parameters, the build, and a timestamp — a tree. An estimated, broadcast, or joined column records its operation and inputs the same way, in the project's element manifests (see the project store). 31Routines — recipes that run recipes

A routine chains saved recipes into one runnable document: refresh the calc columns, then a drift check for each grade of interest, every table filed in the run's own folder under runs/. It is the month-end close as a file — and you don't have to write it. Tools → Recipes → New routine… opens the routine editor; what it saves is a small YAML file you can read back in one glance.

Steps come in two shapes. A plain step runs one recipe, optionally layering overrides on top (a different cutoff count, a series pointed at another column — the ⋯ button on a step). A for-each block runs its steps once per row of a parameter table: add a variable for each thing that changes, a row for each run, and write "$grade" in a step wherever the value should land. + row duplicates the last run so you only edit what differs. There is no scripting here — expansion is plain substitution, so the whole run is knowable before anything executes. That is exactly what Preview shows, and what the optional guard checks: stop before step one if any report it would write already exists.

The preview is not just a listing — each line is clickable. Every for-each row expands to its own line, so clicking one opens that step's tool window configured with exactly that row's values baked in, and nothing runs: tune a drift check against one grade, save it back under the same recipe name, and the whole routine picks up the change. (Calc-column and figure steps act immediately, so those lines don't open.)

A step doesn't have to point at a saved recipe at all. Give it tool: instead (+ inline step in the editor) and its whole setup lives right in the step, under with:. The analyses run without their windows — gt, stats, swath, xy, xtab, resource, validation, pairing, contact, factors, the three QA reports — and so do the producers: export, sections, composite, shell, join, reconcile, pcgrid, cutfill, gridexport, projectgrid, extrude, sectionlines, blockoutlines, plus calccols, solid, figure and the composer's compo. Each computes with the same code as its window, so a step's numbers are the window's numbers — so a batch can be written from scratch, with nothing recorded first. Name a recipe when you'll reuse the setup elsewhere; inline it when it belongs to this routine alone.

The editor writes a file like this (block style, strings quoted — hand-edit or write them from scratch if you prefer):

# micro recipe — routine. Hand-edit freely; series reference layers by NAME.
name: "month-end"
tool: "routine"
params:
  output:
    prefix: "m-"
  steps:
    - guard: "no-overwrites"
    - recipe: "refresh calc columns"
    - each:
        - grade: "FE"
        - grade: "SIO2"
      steps:
        - recipe: "drift check"
          with:
            series:
              - layer: "model_A.csv"
                col: "$grade"

Settings go under with:. A step has a few keywords of its own — as, emit, cache — and everything that belongs to the tool goes under with:: the whole setup for a tool: step, a set of overrides on the saved settings for a recipe: step. An override replaces a setting whole, so give the full series list, not one field of it. Keeping the two apart means one can never be mistaken for the other: a filter: at a step's top level stops the routine before it runs and says to move it under with:. Older files with settings mixed into the step still run; Tools → Recipes → Check all recipes… flags them and rewrites them.

Which rows run — filter

A parameter table usually outlives any one run: benches that are finished, domains you're not reporting this month, a scratch row someone left behind. Rather than maintaining a second copy of the table, give the each block a filter — the same expression language again, deciding which rows fan out:

- each: { from: "params.xlsx#Benches" }
  as: b
  filter: "active = true and bench >= g.floor"   # which rows run
  steps: [ ... ]

The row's own columns are plain names, and any scalars from params are visible too, so a row can be compared against a global. This is data selection, not an if: the rows that run are still decided entirely by the files you can read, never by the result of a step — so Preview still lists every run and the guard still checks every output, exactly as before. A mistyped column in the filter says so out loud instead of quietly matching nothing.

Computed values — ${…}

A $name substitutes a value as it stands. Wrap it in ${…} and you get an expression — the same language as the filter box and the ƒ columns, so there is nothing new to learn:

- recipe: "grade tonnage"
  with:
    nCut: ${g.cutoff * 1.1}                  # arithmetic
    floor: ${if(b.grade = "FE", 55, 45)}     # if(), the same one you use in ƒ
  as: "bench ${b.bench} · ${b.grade}"        # inside text, it interpolates

Expressions compute values, never structure. They can say what a cutoff is; they cannot decide how many runs there are, which recipes exist, or what a report is called. That is deliberate, and it is what keeps a routine honest: the step list is still fully enumerable before anything executes, so Preview still lists every step and the guard still checks every output. A routine remains a document you can read, not a program you have to run to understand.

A mistyped name fails loudly rather than quietly becoming empty — ${b.bnch} reports unknown column: b.bnch — did you mean b.bench? — and dotted names are just names, so $g.cutoff and a real assay column called Fe.pct are spelled the same way.

Nesting — every bench × every grade

An each block is just a step, and its body is a list of steps — so an each inside an each simply nests, and nesting is a cross product: every row of the outer table against every row of the inner one. Give each table an as and its columns get a namespace, which is what keeps two tables apart when they both have a column called cutoff.

steps:
  - each: { from: "params.xlsx#Benches" }
    as: b                                  # → $b.bench
    steps:
      - each: { from: "params.xlsx#Grades" }
        as: g                              # → $g.grade
        steps:
          - recipe: "grade tonnage"        # runs once per (bench × grade)
            with:
              series: [{ layer: "model.parquet", col: $g.grade }]
              bench: $b.bench

Two benches and two grades give four runs, and each report's name carries both values (gt-1040-fe). Contrast that with a single each whose columns are two equal-length lists: that is a zip — the columns are paired, giving two runs, not four. Both are useful and they are easy to confuse, so Preview lists the expansion either way: count the lines and you know which one you wrote.

Parameters that don't fan out

A real parameter workbook holds two kinds of sheet: run tables (one row per run — that's each) and a key→value sheet, usually called General, with a parameter column and a value column. That second kind is a series, not a fan-out: you want its numbers available to every step, not a run per row. That is what params is.

name: "Month-end"
tool: "routine"
params:
  params:
    - from: "params.xlsx#General"    # parameter | value  →  $g.cutoff, $g.density
      as: g                          # namespace (default: the sheet name; "" merges flat)
      index: parameter               # key column   (default: the first)
      value: value                   # value column (default: the second, when there are two)
      fill: 0                        # what an empty cell means
  steps:
    - recipe: "drift check"
      with:
        nCut: $g.cutoff              # a scalar, everywhere
    - each: { from: "params.xlsx#Benches" }
      steps:
        - recipe: "grade tonnage"
          with:
            series: [{ layer: "model.parquet", col: $grade }]
            floor: $g.cutoff         # scalars reach inside each blocks too

params is also a step, not only a header: written in the step list it binds its names forward, for the steps that follow — and written inside an each block it is scoped to that block. Same for the report names: as on a recipe or tool step names its report, while as on an each or params step names a scope.

If the sheet has more than two columns and you don't name a value, the whole row stays reachable: a Domains sheet keyed by domain gives you $d.hem.cutoff and $d.hem.price. Keys are made safe for use as names — dilution factor becomes $g.dilution_factor. A variable from an each row shadows a scalar of the same name, so a run table can override a global. And Preview lists what the params resolved to, so the scope is never invisible.

One Excel quirk worth knowing: a value column with a single blank cell is typed as text by Excel, so micro coerces numeric-looking parameters back to numbers when it reads a routine's tables — 55 stays a number even if the sheet has a gap.

The parameter table has two more spellings for hand-writers: equal-length columns (each: holding one list per variable, zipped row by row — never a cross-product; unequal lengths are an error, not a guess) and from: "params.csv", which reads the rows from a table file in the project — keep the quarter's run matrix as a CSV and the routine stays two lines.

Keeping a result — ⇥ layer

Every analysis window has a ⇥ layer button beside its export buttons. It keeps the result — the grade–tonnage curve, the swath profile, the stats table — as a table layer: something you can filter, join against another run, and export like any other data, instead of a window you look at and close. In a routine, a step with emit: layer does the same automatically, so a month-end run ends with layers you can read, not only files you have to open elsewhere.

Filing layers — a name can be a path

A layer name with slashes in it is a path: name a result swaths/FE drift and it lands in a swaths group (created if it isn't there yet), labelled FE drift. It nests — month-end/gt/FE makes a gt group inside a month-end group — and it works on any layer, not just results: rename a model to models/deposit and it files itself. A plain name with no slash just renames, as always.

This is sugar at naming time, not a new kind of group: once filed, the layer tree is the truth again — drag layers between groups, collapse them, reorder them exactly as before. It means a routine's outputs organise themselves: a step with emit: layer files its result under the routine's own name, and emit: { layer: "swaths/$b.grade" } puts it exactly where you say.

What a step writes, and what stops it

Preview now says what every step writes — a report path, a column on a layer (marked (replaces) if it is already there), a figure, or (opens only) if it writes nothing. The guard checks all of it: a calc-column step that would overwrite an existing column stops the routine before anything runs, exactly as a report file does. Producing operations replace by name rather than refusing, so running a routine twice leaves the same project as running it once.

When a run stops

A long routine that fails at step nine should not cost you the first eight. A stopped run offers Retry step and Skip & continue; a cancelled one offers Resume; and right-clicking any line in Preview runs the routine from that step. Steps that were not run are marked with a dash in the tracker, and the summary says “1 step run (2 skipped)” rather than claiming credit for the whole thing.

Every run writes into a folder of its own, runs/<date> <time> <routine>/: one table per analysis step and the run's record, run.json (see Checks & run records). output: takes dir, prefix, and suffix to steer the naming — a fixed dir means the next run writes over this one's reports, so leave it out unless something outside micro needs a stable path. Calc-column and figure steps run their engines directly. Routines never prompt mid-run: every referenced recipe and layer is checked up front and missing ones are named before anything starts; a failed step stops the routine visibly, its window left open for inspection.

A running routine opens the run tracker: the expanded step list with a live state per line and step n of N in the title. Cancel stops after the current step finishes — reports already written stay written, nothing is left half-done. The window stays open when the run ends (or stops, or is cancelled) as the run's record: what ran, what it wrote, where it stopped.

Ask-me-first recipes — inputs:

Any recipe or routine can declare inputs: — a short list of questions. Running it then opens a small generated form instead of executing immediately: pick the model, pick the column, accept or change the defaults, press Run. The answers flow into the recipe through the same $name markers the for-each table uses, so one saved setup serves every model and grade in the project.

name: "GT — any model"
tool: "gt"
inputs:
  - name: "model"
    label: "Block model"
    type: "layer"
  - name: "grade"
    label: "Grade column"
    type: "column"
    of: "model"
  - name: "ncut"
    label: "How many cutoffs"
    type: "number"
    default: 15
params:
  nCut: "$ncut"
  series:
    - layer: "$model"
      col: "$grade"

Five input types: text (the default), number, choice (with options:), layer (a picker over the loaded layers), and column (a picker over the columns of the layer named by of: — it re-fills live when that layer changes). A marker that is exactly "$name" lands typed — a number input arrives as a number — while markers embedded in longer text become text. Answers are remembered for the session, so the next Run… starts from where you left it.

Routines ask too: declare inputs: on the routine itself — the editor's + ask first section adds them without touching YAML — and the answers substitute everywhere in the steps before the parameter tables expand. Keep input names distinct from the tables' variable names; the questions come first, the table fans out after.

32Checks, comparisons & run records

A routine that writes seven tables still leaves the reading to you: was the bias inside five percent, did any tonnage move by more than a tenth since last month, did the model QA find errors? A check writes such a question into the routine; a compare sets this run's table beside the previous one's. Both are steps, run where they stand, and go into the run's record with what they read and what they concluded.

    - tool: "modelqa"
      with:
        layer: "deposit.csv"
      as: "mq"
    - check: "mq.errors = 0"
      say: "the model has no QA errors"
    - check: "abs(val.bias_pct) < 5"
      level: "warn"
    - compare: "gt"
      tolerance: 0.1
  • On one number — a step's values (the validation's bias, the QA's error count, cut and fill's volumes) are known by its as name and a dot, and the check is an expression in the usual language. A pass carries on; a fail stops the run, or with level: "warn" is recorded and the run carries on. A check can also test every row of a table, or a value against the previous run. A check that couldn't be evaluated is not evaluated, never a pass.
  • Compare — joins a table from this run to the baseline's on its key and writes the two side by side (gt-compare.tsv: each value, _prev, _delta, _pct as a fraction, and where the row was found). With a tolerance it is also a check, naming the offenders (FE · 65: tonnes -11.8%).
  • Baselines and Accept — the baseline is the most recently accepted run of the same routine, else its latest run that finished ok, and is written into the record. When a run finishes the tracker offers Accept as baseline…: your name goes into an accepted.json beside the record. Tools → Recipes → Runs… lists every run with its status, what it was compared with, and who accepted it.

The run record

Every run gets a folder of its own, runs/2026-11-22 1432 month-end/, holding its tables and run.json: what was read (each input file with its SHA-256), every step's settings — automatic values pinned to what was used — its outputs with their hashes, every check and its verdict, the baseline, and the micro build. A table of tonnages is a claim; the record is what lets you, or a reviewer, check it against the files.

The cache. Run a routine twice and the second run finishes almost at once: a step whose inputs and settings are provably unchanged is reused from an earlier run (its output checked intact and copied), and the tracker and record say where from. Reuse looks across every run in the project. Run fresh (reuse nothing) in the routine's submenu, or cache: false on a step or a routine, turns it off — for a final sign-off, say. Layers keep their own memory: see Lineage.

33The library

A routine in a project's recipes/ belongs to that deposit. Your standard model QA, your month-end, the validation you always run belong to you: the library keeps them in this browser, apart from every project. Open it with Tools → Recipes → Library…, with or without a project (without one the menu reads Library… (routines without a project)).

Each entry is a pack: a recipe or routine with everything it needs — the recipes its steps name and the parameter tables they read. To library copies a project recipe in; Into project writes a pack into the open project, never overwriting a file of yours that differs. Both are copies.

A library routine runs on whatever layers are loaded, using its own recipes and tables: Run in project (into the project's runs/), Run → folder… (into a folder you pick, treated like a project), or Run → zip — no project at all: at the end you tick which outputs to download as one zip, and run.json always goes, because the outputs mean little without their record. After zip runs the library keeps the last records, so the next run still compares with a baseline and reuses unchanged steps. A library routine is most useful when it asks for its layer with inputs rather than naming one.

A pack leaves micro as one file: YAML (one self-contained, diffable text file with the recipes and CSV tables bundled in) or zip (the same as separate files, Excel workbooks included) — an office standard you can e-mail and import. The library lives in this browser profile's storage: clearing the site data clears it, so export what you can't afford to lose.

34Figures & decorations

View → Decorations & figure… toggles a scale bar, north arrow, color legend, and title onto the viewport — they show live and are captured verbatim by Export figure (at 1× / 2× / 3× scale for print). Legends are per layer — stack one per model when several share the view, each with its own title. Set a background (white or paper for print; the decorations flip to dark ink to stay readable). The exported PNG is what you see, ready for a report — and it pairs with the lineage report for a fully auditable figure. The analysis plots have their own ⤓ png / ⧉ copy / ⧉ table buttons. For a laid-out page — a stated scale, a caption that fills itself in, a title block, a vector PDF — use the composer.

Section series. With a section on, View → Section series… (or ⌘K “section series”) renders the section again and again across the data — from, to, every so many metres, with the slab you have set — each sheet a figure rendered to convergence with the decorations on and titled with its position (“N–S section 1075 ± 5”, after your own title if there is one). The camera moves with the plane, so every sheet is framed alike. The result is one .zip: a PNG per section, numbered in order, and an index.html that lays them out one to a page for printing. The section, the camera and the title are put back afterwards.

Turntable video. View → Turntable video… (also in the decorations panel, and ⌘K “turntable”) orbits the camera around the current view and saves it as a video — a full turn, the other way, half or a quarter turn; 4 to 20 seconds; 24, 30 or 60 frames a second; screen or 2× resolution; decorations on or off. Every frame is rendered to convergence like a figure, so a big model takes longer to record, but the video still plays at an even speed. The camera returns to where it was, and the video plays in the window to check before you Save video. 35The composer

Export figure is the quick way out: the view you see, dressed. A figure in a report is more — a plan at a stated scale with coordinates on its border, a legend that matches it, the grade–tonnage curve beside it, a caption that says which section and how many blocks, a title block with a drawing number. The composer is micro's page for that, and its output is a vector PDF. Each frame on the page knows where its content came from, so a figure can be made again — with new data, at another resolution, once per bench — without being redrawn.

Open it with File → Composer… (or ⌘K “composer”). A figure is one page (A4 landscape by default; A5 to A2, Letter, Legal, Tabloid or custom) with its frames, saved in the project as figures/<name>.compo.json as you edit; File → Figures lists them. The page bar adds frames, aligns and stacks them, and sets paper, zoom, an optional snapping grid and rulers you pull guides from.

  • 3D view — not a screenshot: it remembers its scene (camera, section, layers, colours, filters, background), renders at its own size and shape, and is rendered again at export. Double-click it to edit the scene in place in the 3D view, inside a dashed outline in the frame's proportions; Update from the 3D view and Show in the 3D view go either way. Making a figure never disturbs your own view.
  • Legend, scale bar, north arrow — follow a view frame; the scale bar is recomputed each time the page draws, and a perspective view says no scale rather than drawing a wrong one.
  • Text and Label — a caption, or a short text pinned to a world point with a leader that stays on it from any angle.
  • Chart and table — sent from any analysis window's ⇥ figure: a chart re-flows when resized and is vector line work in the PDF; a table is set as a book table, and never silently loses its end. Add resource table builds the report table (§19); a stereonet arrives from the structure window; Add image places a logo or a photo.

Captions that fill themselves in

A field is a word in braces the page replaces when it draws: {fig}, {date}, {section}, {layers}, {scale}, {page} of {pages}, {crs}, a house property {prop:client}, and statistics of what the view shows — {count:,} of {total:,} records, {mean:FE:.1f} — counted inside the view's section by default. insert field… lists them all. A caption written with fields describes the figure as it is, not as it was when you typed it.

Drawings, not pictures

  • A locked scale — type 2500 in an orthographic view's scale row and it stays 1:2500 however you resize the frame, on export and on every atlas page. coords adds coordinate ticks (or a grid) on the border, as vectors.
  • Vector sections — right-click a view → Vector section (blocks, drillholes, meshes as vectors) prints the section as line work: each block the plane cuts as the exact shape the plane makes of it (same-coloured neighbours merged), drillholes as bands, meshes as their cut lines. It needs a section, an orthographic camera and a view square to the plane (l); otherwise the status line says which is missing. Settings → display → vector-section outlines draws the blocking itself — every sub-block outlined in ink, or each parent block's cut in a heavier line — for checking a sub-blocked model received from another package.
  • Key plans — + key plan adds a small plan of the whole model with the section's line and slab across it, labelled with its figure number; on every atlas page the line moves with the section.
  • Small multiples — one view repeated, varying the colour column, the section level or the filter, each copy captioned.

House style, data, templates

properties… holds the figure's drawing number and revision and the project's company, client, project, prepared / checked by and disclaimer, which Add title block lays out as an editable ruled block. Every frame records the layers, files and content hashes it was made from: a badge says older data when a layer is now a different file, and Refresh (↻) makes the whole figure again — views re-rendered, charts and resource and comparison tables recomputed, stereonets re-measured (File → Figures → Refresh all figures for every one). A refresh recomputes; it doesn't approve, so read it before you sign it. ⇄ other data… points a figure at different layers and columns, matched by name; ☆ template makes it a starting point for new figures.

Export PDF or Export PNG at 150, 300 or 600 dpi re-renders every view at that resolution. In the PDF, text is text and charts, legends, scale bars, ticks, labels and vector sections are line work. By default the PDF carries its figure inside it: drop it on micro a year later and it opens as an editable figure, its badges saying whether the loaded data is the data it was made from. Untick embed figure for a deliverable that should hold only the page. In a routine, the compo tool prints a page with the data loaded at that moment.

36Atlases

A set of bench plans is forty figures that differ in one number. An atlas is one composed figure printed once per row of a table: the figure supplies everything that stays the same, the table what changes — a section position, a filter, a camera — and the pages are bound into one PDF. Its machinery is a routine, so an atlas is a file you can read, rerun and keep with the project.

Build one good page first: a 3D view showing the section you want to step, its legend, scale and north, a caption. Then press atlas… in the composer's figure bar (the project must be saved). micro writes a starter routine and opens it in the routine editor: it steps along the axis of the view's own section, across the extent of what is loaded, gives each page a slab, collects the pages into atlas/<figure>.pdf, and hands each page its position as level. Write ${level} in a caption, check the levels (the first guess spreads them over the bounding box, not over your benches — list your bench midpoints and set the thickness to match), press Preview, then Run.

A page can change its section, its camera or its filter — a page per bench, per cross-section, or per domain — and two at once by nesting or zipping the tables. Note — Charts and tables on an atlas figure are printed as they stand, the same on every page. Statistics that should change with the page belong in caption fields.

The run's record lists each book with its page count and SHA-256, and the book carries its figure inside it like any composer PDF. book binds the pages into one PDF; out writes a file per page (put the row's value in its name). Because an atlas is a routine, it sits naturally at the end of a longer one: check the model, recompute the columns, then print.

37Projects

In a Chromium browser, File → Open project folder keeps your layers, styling, filters, selections, camera, section, bookmarks & scenes — and your open analysis windows (see Windows) — in a plain folder (project.json + the data files). Ctrl+S saves.

The folder is organized by data kind — models/ drillholes/ clouds/ meshes/ grids/ tables/ polygons/ — beside figures/, recipes/ and runs/, with each file's manifest and sidecars beside it (see the project store). Tidy project folder migrates an older flat project in place, and Scan folder for new data treats the folder as an inbox: drop a file in by hand (or from another tool) and micro picks it up. A loose layer (opened from outside the folder) offers Copy into project from its context menu — always with a sized consent step, never silently.

The inbox handles new files; Reload from disk (a layer's context menu) handles changed ones. If a file was edited outside micro — a model re-run, a parameter table updated in another tool — reload re-reads the fresh bytes through the layer's existing setup: column mapping, styling, calc columns, filter, and surface state all ride through. Edit a routine's parameter CSV, reload it, run the routine again — the whole loop without reopening anything. Drag-dropped files can't reload (they're snapshots with no path), and if the file's size changed, micro notes that painted and materialized columns — which attach by row position — may be stale.

Change file… (same menu, and the palette) points a layer at a different file and keeps everything else: next month's model drops in under last month's setup. The layer keeps its place in the tree, its label, colour, ramps, calculated columns, filter and its views; its name becomes the new file's (the name is the file, the label is yours). A delimited file keeps the old coordinate, grade and category columns by name, so a re-ordered header is fine, and sniffs whatever is missing. Painted columns and the selection were made record by record on the old file, so micro asks before dropping them. The new file must hold the same kind of data — a block model for a block model, a grid for a grid; anything else opens as a new layer instead. Drillhole sets change their tables from the set's own menu.

Export rows… writes any layer back out — scope all / filter matches / selection, every column including calculated, painted, estimated, and joined ones, as CSV or Parquet. Opening a .dm and exporting is the .dm→CSV (or →Parquet) converter.

Bookmarks & scenes — save where you were looking

Two ways to save a view, under View → Bookmarks and View → Scenes. A bookmark is a viewpoint — camera + section — the quick nav aid: drop a few (Save bookmark…), or press g then Shift+1–9 to save the current view into a numbered slot — and g then the digit jumps back to it (a bare digit deliberately does nothing, so a stray keystroke can't teleport the camera). A scene is the full working state — camera + section plus each layer's visibility, color-by, and filter, so applying one puts the whole scene back the way it was (Save scene…, or Save scene (with selection)… to also pin the 3D selection). Applying a scene names any layer it wanted that isn't loaded, and skips it. Both live as small JSON files in the project folder — bookmarks/ and scenes/, one per entry — so they travel with the project, are hand-editable, and get picked up by Scan folder for new data. There is no fly-through: applying a view snaps straight there.

38Backups & project packs

File → Back up project… writes the project folder into a single <project>-<date>.zip.micro: to move a project to another machine, hand it to a colleague, or keep a dated copy before a big change. It's an ordinary zip (rename it .zip and any tool opens it), streamed to disk as it's written, so a project with multi-GB models never has to fit in memory. Everything in the folder goes in, including files you dropped there yourself. Lean leaves out the caches micro rebuilds by itself (the discovery and display caches), at the price of re-reading a big model once when the restored project first opens; Full keeps them. The backup is made from the folder, so with unsaved changes micro offers to save first. Layers linked from outside the folder aren't in it: the dialog names them. To include them, save the project and choose Copy into project when it asks.

A backup is also a project pack: you can open it without unpacking it. File → Open project pack…, or opening a .zip.micro like any other file and choosing Open (read-only), opens the project straight from the one file: every model, hole set, bookmark, scene and recipe, the filters and styles as they were saved. Nothing is unpacked, because micro reads each file where it sits inside the pack, so a pack of several gigabytes opens as quickly as the folder it came from. It doesn't need folder access either, so it works in browsers that can't open project folders at all, which makes a pack the way to hand someone a project to look at. You can still work in it — filter, paint, bookmark — and those changes are kept for the session beside the pack, which itself never changes. To keep them, Save asks for an empty folder, writes the whole project there with your changes, and carries on in that folder as a normal project. Because files read straight from a pack skip the checksum, micro reads the whole pack through once in the background after it opens and says in the status line whether every file is intact; a damaged one is named.

File → Restore project from backup… (or Unpack to a folder… when you open a .zip.micro) shows what the backup holds, asks for an empty folder, unpacks into it and opens it as the project. Every file is checked against the checksum it was written with, so a damaged backup stops with the file's name instead of restoring wrong data. micro won't restore into a folder that already holds a project, or over a file that's already there.

Parquet — the model store

Store as Parquet… (right-click a CSV/.dm model) converts it Morton-sorted, so each row-group's footer becomes a tight spatial index and queries skip whole row-groups they can't match. The dialog says exactly what will happen — per-layer rows, sizes, and a keep original option — and the same conversion runs when you save a project (a one-time, remembered choice: always / ask / off). Painting stays editable through the reorder, the file self-describes (grid, extents, categories in its metadata, so it reopens with no discovery pass), and the whole thing round-trips. Parquet block models also open streamed, holding nothing decoded, with predicate and spatial push-down on the filter.

The element manifest — the data model on disk

Beside each data file the project writes <file>.element.json: a readable description of the element — its geometry interpretation, its record locations (a drillhole set lists collars, vertices, and one location per interval table, related by the hole id; a grid lists its lattice with coordinates implicit), its columns, and an ops list: every derivation (a calculation's expression, an estimate's method and parameters, a broadcast's source column, a join's inputs) recorded as data. The ops list is the audit trail — open the JSON and read exactly how every derived column came to be. It's also how the project restores: definitions reload from the manifest, and derived data that's missing or stale is simply re-derivable. Stale is decided by content: each derived file records a fingerprint of the source it was made from (a hash of samples taken across the file, so even a multi-gigabyte model costs only a few small reads). A copy of the same bytes still matches, however new its date; a re-export that changes values but keeps the file the same size doesn't, so painted and materialized columns aren't laid back onto data they no longer describe.

Column sidecars

Derived columns that carry data — estimates, materialized calculations, joins, broadcasts, painted domains — live in a <file>.cols/ folder as one Parquet file per column (numeric as floats, categories as strings). Small, typed, self-describing, and readable by anything that reads Parquet.

Sidecars & the memory budget

Files in a project also get a small .meta.json sidecar at save time: the discovery result (grid, extents, sub-blocking, categories — reopening skips the sweep entirely, even on a 13 GB .dm), column statistics, and a band index that lets filters skip stretches of CSV/.dm files that provably can't match. Sidecars are a cache: delete one and micro re-scans.

In memory, scanned columns pin into a budgeted cache (View → Filter column cache: off / auto / a size in MB — auto scales with your machine) so repeat filters and widget drags run with no file reads; derived-column values share the same budget and quietly reload from their sidecars when evicted. The memory panel (Help → memory) shows what's held.

42Questions & troubleshooting

“The system reset the 3D graphics.” A phone short of memory, a laptop waking from sleep or a graphics-driver reset can take the 3D context away; every layer's copy on the graphics card goes with it, but the session itself is untouched. When the browser hands the graphics back, micro rebuilds the view on its own — it saves the session into a folder in memory (files linked, never copied) and reopens it, so layers, styling, filters, calculated and painted columns, selections, views, the section and the camera come back as a project reopen brings them. Your project folder, if one is open, stays the project, marked as having unsaved changes. If the graphics never come back, the bar offers save project and reload.

Which browsers work? Current Chrome, Edge, and Firefox all run micro. Project folders, disk mounts, and Save-as need a Chromium browser (Chrome/Edge) — Firefox opens and analyzes everything but can't hold a folder connection.

How big is too big? There isn't a hard limit — micro streams, so opening is near-instant at any size and memory stays bounded. The practical costs are per-scan: the first filter or analysis over a huge CSV reads the file once (a 13 GB Datamine file is a few tens of seconds), after which sidecars, push-down, and the pin cache make repeats fast. For models you'll work with daily, Store as Parquet… is the single biggest speedup.

My filter is slow on a CSV / .dm. Run Build index (right-click the layer) or just save the project — the band index lets filters skip file regions that can't match. Or convert to Parquet, which also gets spatial push-down.

micro looks memory-hungry / I want it leaner. View → Filter column cache sets the budget (off / auto / a size). Cached columns and derived values evict under the budget and reload from disk when needed; off disables caching entirely. Help → memory shows what's held.

A numeric column isn't offered for color / grade–tonnage. The type sniff read it as text (a stray unit string or thousands separator will do it). Right-click the column in Properties → columns → Number.

LAZ files? Not yet — micro is deliberately free of compiled decoders (see Sealed), and LAZ needs one. Convert to LAS, or export XYZ.

Rotated block models? They draw as true rotated boxes. When micro finds a rotated lattice it asks first — boxes or points — and a file that declares its lattice is checked against every block. See Block models.

My CSV uses commas for decimals. A ;-separated file with 1,5-style numbers is detected and read as numbers; file info says which decimal mark it found. See Columns.

I removed something by mistake. Ctrl/⌘Z brings back a selection, a filter, a ƒ column, a rule, or a paint stroke — see Windows, undo & safety nets.

Sub-blocks come up as points. Detection needs per-block dimension columns (dX/dY/dZ or XINC/YINC/ZINC). Any whole-number refinement works, odd ratios included, but a block may span at most 255 fine steps along an axis; a model past that falls back to centroids and says why — everything still works, blocks just draw as points. See Block models.

Can I run it fully offline / air-gapped? Yes — that's the design. Download micro.html, copy it anywhere, double-click. Nothing phones home either way; the offline copy just makes it visible.

Something looks wrong / a file won't open. i (file info) shows what micro detected — column mapping, grid inference, parse warnings. Most import surprises are visible there, and the mapping can be corrected in place.

Tools and routines. The analyses a routine runs are available without their windows. Layers are named as a routine names them, by name.

micro.tools()                          // [{ name, label, params, outputs }]: gt, stats, swath, validation, resource
await micro.runTool('gt', { layer: 'model.csv', series: [{ col: 'AU', weight: 'DENS' }], cutoffs: [0.3, 0.5, 1] })
  // → { table: { columns, rows, key, units }, values, resolved, warnings }
micro.routines()                       // [{ name, file, inputs }]
await micro.checkRoutine('month end', { inputs: { grade: 'AU' } })
  // → { steps: [line…], problems: [..] }: the dry run, nothing runs or is written
await micro.runRoutine('month end', { inputs: { grade: 'AU' }, onStep: (s) => … })
  // → { status: 'ok' | 'failed' | 'cancelled' | 'refused', record, problems?, error? }
await micro.runs()                     // [{ dir, routine, status, started, finished, baseline, accepted }]
await micro.acceptRun(dir, 'A. Name')  // the baseline the next runs compare with

A tool's numbers are the ones its window and a routine step give. An unknown setting is refused, naming the nearest real one. runRoutine never prompts: a routine's inputs are given up front, and a missing one rejects. It resolves when the run ends, however it ends, with a copy of the run record (runs/<date> <time> <routine>/run.json): the SHA-256 of every input file and output, every step's settings, values and checks. A run that stopped at a check resolves as failed.

Ids can change, and the API follows them. Re-reading a drillhole layer (a new colour channel or category, a re-desurvey) or a few other re-reads (Reinterpret as, Reload from disk, a grid band) replaces the layer with a new one, with a new id. micro:layer-replaced says so, the new layer keeps its place in the layer tree, and any API call given the old id acts on the new layer. setColorBy resolves to the id the layer has afterwards.

Groups. A group is a path of names. addLayer({ …, group: 'Model/Domains' }) and open(file, { group }) file a new layer into it, creating the groups on the way; group(path, ids) moves existing layers. A group exists while it holds layers, so there is no empty group to make. A drillhole layer moves with its whole set.

Embedding. micro.html?embed=1 hides the title and the Sealed badge from the first paint; setChrome changes that later. Hiding the badge in an embed is the honest default: Sealed is a claim about micro's own page, and a same-origin host page can read everything micro holds and has a network of its own. Help → Why it's Sealed stays either way.

Presenting. setChrome({ presenting: true }) hides every bar, panel and analysis window, and the canvas takes the whole window; the camera doesn't move. The decorations stay, since they're drawn on the picture, so turn on the ones you want with setDecorations. Orbit, zoom and pick still work. A dialog that asks a question still shows. presenting: false brings back exactly what was open, and layers, filters, the section and the selection are untouched throughout. Each micro pane takes its own call.

Handing micro a layer: addLayer

When the data comes from software that already knows what it is, write no file. Pass columns and their meaning. Nothing is sniffed: no name guessing, no grid discovery.

const id = await micro.addLayer({
  kind: 'blocks',                       // 'blocks' | 'points' | 'mesh' | 'drillholes' | 'table'
  name: 'Au_OK',
  columns: {                            // one length; any number of value columns
    E: Float64Array, N: Float64Array, RL: Float64Array,
    Au: Float32Array,
    LITO: { codes: Uint8Array, labels: ['Granito', 'Skarn'] },   // a category, already coded
  },
  roles: { x: 'E', y: 'N', z: 'RL', value: 'Au', category: 'LITO' },
  lattice: { … },                       // optional — the DECLARED lattice (below)
  sizes: { dx: 'DX', dy: 'DY', dz: 'DZ' },   // optional — sub-block sizes: column names, arrays or constants
  frame: { crs: 'EPSG:31983' },         // optional
});
  • Columns: typed arrays (any of Float64Array, Float32Array or the integer kinds), plain arrays of numbers or strings, or { codes, labels } for a coded category. The category keeps your label order.
  • kind: 'mesh' takes vertices (a Float64Array of x,y,z triples) and triangles (a Uint32Array of index triples) instead of columns.
  • kind: 'drillholes' takes three tables, collar, survey and intervals, each { columns, roles }. The roles are: collar bhid x y z (+ optional eoh); survey bhid at az dip (depth works for at); intervals bhid from to (+ optional value, category). Optional method and dipConvention are as in the import dialog.
  • kind: 'table' takes columns only. A free-text table belongs here, not inside a spatial layer.

Big data: pass a file, not columns. Give file instead of columns: a File, a Blob or a FileSystemFileHandle. The file is opened in place, never copied and never held decoded (CSV, Parquet and .dm stream from it). Roles name its header's columns.

await micro.addLayer({ kind: 'blocks', file, name: 'Au_OK',
  roles: { x: 'EAST', y: 'NORTH', z: 'RL', value: 'AU' },
  lattice: { basis: { … } },            // CSV / Parquet; checked against every record
  sizes: { dx: 'SX', dy: 'SY', dz: 'SZ' }, // column NAMES (a .dm's are XINC/YINC/ZINC)
  format: 'parquet' });                 // only when the file's name has no extension
  • A handle is kept with the layer, so project save and Reload from disk use the real file.
  • A File made in the host's own frame works too: micro duck-types the file and doesn't rely on instanceof.
  • Meshes (.ply .obj .msh .lfm .wfr .dxf) and tables (delimited or .xlsx) take file the same way.
  • Each drillhole table may be { file, roles } or { columns, roles }, and the two can be mixed.
  • sizes and lattice can't be given together: a sub-blocked model's fine lattice is measured from its sizes.
  • Without a declared lattice, a detected rotation still asks first. Pass acceptLattice: true | false to decide in advance.

The layer is a file-backed layer. micro writes the columns once into its own formats (Parquet for blocks and points, with a micro:model footer; binary PLY for meshes; RFC 4180 CSV for drillhole and plain tables) and opens them with every role stated. Pick, colour-by, filters, stats, grade–tonnage, swath, sections, export and project save therefore behave exactly as for a file, and there is no second code path to drift.

Success and failure come back to you. addLayer resolves to the layer id once the layer is complete. The first layer's id is 0, so test for null, not truthiness. It rejects with the error micro would otherwise show, and still shows it on the status line. The same holds for files:

const id = await micro.open(file, { name });                 // id; rejects with the reason
addEventListener('micro:layer-added',  (e) => e.detail);   // { id, name, kind }
addEventListener('micro:layer-failed', (e) => e.detail);   // { name, error }
addEventListener('micro:lattice-rejected', (e) => e.detail);   // { name, reason } — a declared lattice refused

The layer starts coloured by what you named. With roles.category it is coloured by the category; else, with roles.value, by the value; else by elevation. colorBy: 'column' in the spec chooses for you, and setColorBy changes it later. palette and colorRange in the spec set its scale, as setPalette and setColorRange do; a wrong one rejects and leaves no layer.

Several categories. A block model carries several text columns (lithology, weathering, domain). roles: { …, categories: ['LITH', 'WX', 'DOMAIN'] } offers each in micro's colour-by list. The first opens as the category unless roles.category names one, and choosing another re-reads the model with it as the category, as setColorBy(id, 'WX') does. For drillholes, put categories in the interval table's roles.

Hearing what the user picked. When the user clicks a record in the view or selects a row in an attribute table, micro fires micro:pick on window. Read the record's values with row(layer, rec):

addEventListener('micro:pick', async (e) => {
  const d = e.detail;   // { layer, rec, face, world: [x, y, z] | null, source: 'canvas' | 'table' }, or null
  if (!d) return clearMyView();          // a click on nothing, or the record panel closed
  const row = await micro.row(d.layer, d.rec);   // { AU: 1.2, LITO: 'BIF', … }
});
  • rec is micro's record number, which is not necessarily your row: micro may reorder a Parquet file spatially. Carry your own key in a column and read it from the row.
  • world is in world coordinates. face is the block face that was clicked, when known.
  • A click on a mesh gives { layer, rec: null, kind: 'mesh', world }: the point on the surface.

The other direction: await micro.pick({ layer, rec, frame: true }) highlights the record, shows its panel, reveals it in an open attribute table and, with frame, centres the view on it, keeping the zoom. It resolves to the record's world position and rejects on an unknown layer or record. It does not fire micro:pick, so a host that answers picks by picking can't loop.

A Parquet file that states its lattice: micro:model

micro reads the micro:model key-value entry from any Parquet file's footer, not only its own exports. A producer that knows its block model's lattice can write it, and the file then opens with no discovery sweep. The value is JSON:

keymeaning
bboxrequired{ min: [x,y,z], max: [x,y,z] }: the model's extent (it frames the view).
gridrequiredThe lattice, or null for points. Axis-aligned: { x, y, z }, each { origin, pitch, count } with origin the centroid of block 0 (not its corner). Rotated: { basis: { origin, U, V, W, counts, source? } } (below).
categoriesoptionalThe category column's distinct values (≤255), in the code order you want.
subBlockedoptionaltrue for variable-size blocks. Then grid is the fine lattice (pitch = half the size step per axis — the smallest size ÷ 2 when it divides the others) and you must also write dims. Every size must be a whole number of fine steps, at most 255.
dimswith subBlocked{ x: 'DX', y: 'DY', z: 'DZ' }: the size columns by name.
sizeQMax, sizeShapesoptionalDescriptive: the largest size per axis in fine steps, and how many distinct shapes. Any number of shapes is fine (an older dimPalette is accepted and ignored).
declaredoptionalWho states the lattice (e.g. "mm"). A declared or rotated lattice is applied without asking, but checked (below).
voptionalFormat version; 1 today.

A sub-blocked model written without dims is not trusted: micro runs discovery and rebuilds it. Its size columns are found by the same names as in a CSV (DX/DY/DZ, XINC…, DIMX…), so sub-blocked Parquet also works with no micro:model at all. The micro:frame entry ({ crs }) carries the coordinate system.

Rotated block models

A model whose lattice axes aren't east/north/up is drawn as true rotated boxes with exact picking and true sections. The rotation is stored as a basis, never as angles:

"grid": { "basis": {
  "origin": [x, y, z],                  // the CENTROID of block (0,0,0), world coordinates
  "U": [ux, uy, uz], "V": [vx, vy, vz], "W": [wx, wy, wz],   // world vectors = block size × direction
  "counts": [nu, nv, nw],
  "source": { "convention": "azimuth/dip/pitch (ZXZ, clockwise from north)", "angles": [a, b, c] }
} }
  • Convert your angles once to U/V/W. source is kept for provenance only and micro never reads angles back. U, V and W must be perpendicular: a sheared lattice is refused, not approximated.
  • A declared lattice is your statement, not micro's guess, so no confirmation is asked. micro still maps every centroid through it. If one falls off the lattice (more than a thousandth of a block), the declaration is refused, the model opens as points, and the status line says which record and by how much. addLayer with a wrong lattice rejects in the same way.
  • No declaration? micro tries to infer one: nearest-neighbour displacements give the directions, then a fit over every record measures the sizes and checks the lattice. An inferred rotation is never applied silently. micro asks “rotated boxes or points?”. Hosts can answer in advance with openBlob(…, { acceptLattice: true | false }).
  • Exports write the lattice back (the internal form plus this basis form), so a rotated model round-trips through Parquet and project save. The layer's lineage and element manifest record whether the lattice was inferred or declared, and who confirmed it.
  • What works on a rotated model: everything per-record (filters, stats, grade–tonnage, swath, export, select/flag by solid per centroid) and joins and reconciles between models on the same rotated lattice. Not yet: resampling between different orientations (the join panel says so) and the empty-grid creator.
